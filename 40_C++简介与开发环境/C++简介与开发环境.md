## 一、为什么需要它

构造一个会真实发生的碰壁场景：你刚学完 C 语言，打开一份竞赛模板，前两行是 `#include <iostream>` 与 `using namespace std;`——`iostream` 是什么？`std` 是什么？为什么没有 `printf`？更要命的是比赛现场：评测机不给你开 Visual Studio 的图形界面，只给一条 `g++ a.cpp -o a` 的命令行，你连怎么把代码变成能跑的程序都不知道——代码写对了，却卡在"跑起来"这一步，比题不会做还冤。

本篇讲 4 个知识点：从 C 到 C++ 增加了什么、编译运行流程与 IDE、头文件与命名空间、竞赛环境配置。顺序理由：先立语言认知（知识点 1），再打通"代码到程序"的流水线（知识点 2），然后读懂流水线入口处那两行神秘代码（知识点 3），最后把环境钉死（知识点 4）。本篇是纯概念篇，代码只做最小演示，语法细节从下一篇《第一个C++程序》（同批）正式开讲。

## 二、知识点逐讲（每个知识点一节，共 4 节）

### 1. 从 C 到 C++：增加了什么

前置依赖：C 语言基础语法（变量、循环、函数、数组、指针、struct——见 [[C语言要点与内存管理]]）
后续衔接：（同批）《第一个C++程序》的程序骨架、（同批）《数据类型与内存表示》的类型系统

**① 它解决什么问题**

A 源 p3：20 世纪 80 年代，AT&T 贝尔实验室的 Bjarne Stroustrup 博士在 C 语言基础上开发出 C++。C++ 读作 "C 加加"（C Plus Plus）——名字本身就是定位：**在 C 后面加东西**，保留 C 全部优点的同时增添面向对象编程机制。解决什么问题：C 语言写小程序高效利落，但写大程序时"数据和函数分家"导致维护困难——C++ 把数据和对数据的操作打包在一起（封装），并提供继承、多态等机制，让大中型软件的结构清晰、可扩充（A 源 p6）。竞赛视角：你不需要立刻会面向对象，但需要知道 C++ 是 C 的超集——**C 代码几乎不用修改就能以 C++ 方式编译**（A 源 p4），所以你已有的 C 基础全部保值。

关键性质融入正文交代：C++ 同时支持面向过程、面向对象、泛型三种编程风格（A 源 p7）；运行效率仅比汇编慢 10% 到 20%（A 源 p6）——这就是竞赛选它而不是更"高级"的语言的原因。

**② 直觉理解**

模型级类比：**C++ 是"C 这台手动挡车"的升级款**。发动机、底盘（过程式核心、运算符、指针）原封不动，车厂加装了自动变速箱（面向对象）、导航（标准库 STL，后续篇讲）、定速巡航（模板泛型）。老司机开新车不需要重新学驾驶，旧的肌肉记忆全部有效，新功能按需取用——这正是 A 源 p7 说的"尽可能与 C 兼容，提供一个从 C 到 C++ 的平滑过渡"。

用具体内容跑一遍：C 里排序十个数要自己写循环或调 `qsort` 配比较函数；C++ 里是 `sort(a, a+10)` 一行。功能等价，代码量差一个量级——"增加的东西"在竞赛里的第一价值就是**写得快**。

**③ 原理与推导**

A 源 p5 给出一幅四象限的改进图，逐象限推导"加了什么、为什么加"：

| 象限 | 内容 | 为什么需要（设计动机） |
|------|------|----------------------|
| 继承自 C | 简洁紧凑、运算符丰富、目标代码质量高、可移植性好 | 保底：不丢存量用户与存量代码 |
| 对 C 改进 | 编译器更严格、引入引用、const 常量与内联函数取代宏定义 | C 的宏没有类型检查，`#define PI 3.14` 出错无从查起；const 有类型，编译器能帮你抓住错误 |
| 面向对象 | 封装、继承、多态、函数重载、运算符重载、模板（泛型） | 大程序需要"数据和操作绑在一起"才能管得住规模 |
| 扩充 C | 内联函数、函数重载、名字空间、new/delete、引用 | 同名函数各管各的类型（重载）、大型项目的命名冲突（名字空间）、更安全的内存管理（new/delete） |

其中"早期 C++ 没有 自己的编译器"（A 源 p4）值得专门回答一个"为什么"：早期它叫"带类的 C 语言"，靠一个叫 cfront 的预处理程序先把 C++ 翻译成 C，再用 C 编译器编译。这段历史解释了为什么 C++ 最初的一切新特性都能还原成 C 写法——也解释了本系列笔记为什么坚持"每个 C++ 新特性都给 C 等价写法"：这条还原通道至今畅通。

**④ 代码演示**（纯概念篇：最小可运行示例 + 执行追踪表）

同一件事的 C 写法与 C++ 写法对照（自编示例）：

```cpp
// 同一件事的两种写法（自编示例）——上为 C，下为 C++
#include <stdio.h>                    // C：引入输入输出声明
int main() {
    int x = 666;
    printf("%d\n", x);                // 格式化输出，%d 手工指定类型
    return 0;
}
// ---- 以下为等价的 C++ 写法 ----
// #include <iostream>               // C++：输入输出流头文件
// using namespace std;              // 引入标准命名空间 std
// int main() {
//     int x = 666;
//     cout << x << endl;            // 流插入：编译器按 x 的类型自动选输出方式
//     return 0;
// }
```

**执行追踪表**（两份代码各自的"动作链"，n=1 行输出的小数据）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | `#include` 行 | 预处理器展开头文件 | 把头文件内容原地粘贴 | 声明可见 |
| 2 | main 入口 | x 在栈上分配 | `x = 666` | x 就绪 |
| 3 | 输出行 | 流/格式串就位 | C：按 %d 解析；C++：按类型重载 | 字符 "666" 送出 |
| 4 | return 0 | 栈帧回收 | 程序正常结束 | 控制权交还系统 |

**错误写法对照**：

```diff
- #include <iostream>
- int main() { printf("%d\n", 666); return 0; }        // 坑1：用了 iostream 却调 printf 且不引 cstdio——多数编译器能碰巧过，但依赖的是间接包含，换环境就崩（编译错误或链接错误）
+ #include <cstdio>                                     // 用 printf 就显式包含 cstdio（C 的 stdio.h 在 C++ 中的对应名）
- #define PI 3.14                                       // 坑2（C 习惯）：宏常量无类型，编译器查不出 PI 相关错误（隐患）
+ const double PI = 3.14;                               // A 源 p5"const 取代宏定义"：有类型、有作用域、可调试
```

**⑤ 典型应用**（本篇为概念篇，无对应 OJ 题，给自编练习与竞赛衔接）

- 自编练习（自编）：把写过的一个 C 程序（如"读入 n 个数求和"）改用 `cin`/`cout` 重写，目标不是学会流（下一篇讲），而是体会"C++ 编译器能编译你的 C 代码"——同一份文件扩展名改成 `.cpp` 后用 g++ 编译，观察是否直接通过。
- 竞赛衔接说明：竞赛题解与模板全部以 C++ 写成，四象限图决定了后续每篇会遇到哪类新语法——改进象限（const、引用）出现在函数传参，扩充象限（namespace）出现在模板开头，面向对象与泛型象限（STL）出现在数据结构篇（[[链表]]、[[栈与队列]] 等）。

**⑥ 坑点与边界**

> **【易错】** 认为"C++ 是全新语言，C 的知识要推倒重学"。后果：白白丢掉存量能力。事实是 C 是 C++ 的主体部分（A 源 p4），C 代码几乎不改就能按 C++ 编译。

> **【易错】** 把 `const` 和 `#define` 混为一谈继续用宏。后果：类型错误被掩盖、调试困难；A 源 p5 明确"引入 const 常量和内联函数，取代宏定义"。

> **【注意】** C++ 与 C 是两门独立语言（A 源 p4），"几乎不用修改就能编译"不等于"完全兼容"——个别 C 写法（如某些隐式转换）在 C++ 下更严格，编译器会报错。报错时按错误信息改写即可，本系列后续篇会逐个遇到。

> [!example]-
> **边界数据集（纯概念篇：以"能否编译"为边界验证，先自己试，再展开对照）**
> 1. 空输入：源文件只有一个 `int main(){return 0;}` → 编译通过，运行无输出（预期：exit 0）。
> 2. 单元素：只有一行输出语句的 main → 输出一行后结束（预期：不崩）。
> 3. 全相同：两份完全相同的 C 代码分别存为 `.c` 与 `.cpp` 编译 → 都通过（预期：C 超集成立）。
> 4. 严格递增：逐行往 C++ 文件里加新特性（cin、引用、auto……）→ 每加一行重编译，第一次报错处即当前知识边界（预期：定位学习缺口）。
> 5. 严格递减：从 C++ 文件逐行删到只剩 main 骨架 → 始终可编译（预期：骨架自足）。
> 6. 极值：故意混用——`.cpp` 文件里写 C 风格 `char *s = "abc";` 与 `const char*` 混用 → 新标准报错或警告（预期：体会"编译器更严格"）。

回扣开场：现在你知道模板前两行不是天书——它们分别是"扩充象限"的头文件机制与"名字空间"机制。接下来看这套代码是怎么一步步变成可执行文件的。

### 2. 编译运行流程与 IDE

前置依赖：知识点 1（C 与 C++ 的关系）、文件与命令行基本操作
后续衔接：（同批）《第一个C++程序》的编译错误初体验、[[复杂度分析与递归]]（-O2 对常数的影响）

**① 它解决什么问题**

你在编辑器里写的是文本（源代码），机器只认二进制指令（可执行文件）——**从文本到指令的翻译流水线**就是本知识点的内容。解决两个实际问题：第一，看懂编译器报错发生在哪个阶段，才能对症下药（语法错在编译期，链接错在链接期，运行崩在执行期）；第二，竞赛环境只有命令行时，你要能用一条命令完成全流程。这一段属补充：章 2"开发环境介绍"素材缺课件 PDF（附录 B-2 登记），流程按通识补讲，其中"g++ 可直接编译 C++"在附录 B-4 有实测。

关键性质：整个流程分四阶段——预处理、编译、汇编、链接；g++ 一条命令把四阶段全部串完，日常只需记住一条命令。

**② 直觉理解**

模型级类比：**出版一本书**。源代码是作者的手稿（人话）；预处理是编辑统一处理所有批注和引用（`#include`、`#define`）；编译是把中文手稿翻译成"英文大纲"（汇编代码，接近机器但仍有助记符）；汇编把大纲排成标准格式的"活字版"（目标文件 .o，二进制但还不完整）；链接是装订车间——把你的版和你引用的别人章节（标准库）合成一本能发行的书（可执行文件）。

用具体文件跑一遍：`a.cpp`（3 行的 hello 程序）进流水线 → `a.cpp` 展开成上万行的翻译单元 → 编译出汇编 → 汇编出 a.o → 链接 iostream 的库代码 → 出 `a.exe`。手稿 3 行，成书上万行——差距全在链接阶段从库里装订进来的东西。

**③ 原理与推导**

```text
a.cpp ──预处理──> 展开后源码 ──编译──> 汇编代码 ──汇编──> a.o ──链接──> a.exe
        (#include/#define/条件编译)   (语法检查+翻译)    (二进制目标文件)   (接上标准库)
```

文字版推导链：预处理器逐行扫描，遇到 `#include` 就把头文件内容原地展开（这正是知识点 3 的机制基础），遇到 `#define` 做文本替换；编译器接着做语法检查并把 C++ 翻译成汇编——你平时看到的 "error: expected ';' before '}'" 全发生在这一阶段；汇编器把汇编变成二进制的目标文件；最后链接器把目标文件与标准库（cout 的实现就住在里面）拼成可执行文件——"undefined reference" 类错误发生在这一阶段，说明你**用了个名字但没告诉链接器实现在哪**。

为什么设计成四阶段而不是一步到位？**设计动机**是分工复用：每个 `.cpp` 可以独立编译成 `.o`（改一个文件不必全工程重编），标准库只编译一次人人共享（这就是为什么你从没写过 cout 的实现，却能直接用）。IDE（如 Visual Studio）做的事，本质是把这四步包进一个按钮——"生成"就是四阶段连跑。

**④ 代码演示**（最小可运行示例 + 执行追踪表）

```cpp
// hello.cpp —— 最小可运行示例（自编示例，附录 B-4 实测输出 hello world!）
#include <iostream>
using namespace std;
int main() {
    cout << "hello world!" << endl;
    return 0;
}
```

命令行两步（g++ 路径 `C:\mingw64\bin\g++.exe`，本机实测）：

```bash
g++ -std=c++17 -O2 hello.cpp -o hello.exe   # 编译+链接一条命令
./hello.exe                                  # 运行
```

**执行追踪表**（对 hello.cpp 执行 `g++ -std=c++17 -O2 hello.cpp -o hello.exe` 的阶段追踪）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | `#include <iostream>` | 预处理阶段 | 原地展开头文件 | 翻译单元数万行 |
| 2 | 全部语句 | 编译阶段 | 语法检查并翻译 | 通过则产汇编 |
| 3 | 汇编代码 | 汇编阶段 | 生成二进制 | 临时目标文件 |
| 4 | 目标文件+标准库 | 链接阶段 | 拼接 cout 实现 | 产出 hello.exe |
| 5 | ./hello.exe | 运行期 | 执行 main 到 return 0 | 打印 hello world! |

**错误写法对照**（命令行与阶段错位）：

```diff
- g++ hello.cpp                               // 坑1：不带 -std 按旧标准编译，auto/范围for 等新语法报错（编译错误）
+ g++ -std=c++17 hello.cpp -o hello.exe       // 显式指定 C++17，竞赛标准做法
- g++ -c hello.cpp                            // 坑2：-c 只生成目标文件不链接，直接运行会找不到 exe（流程断在链接前）
+ g++ hello.cpp -o hello.exe                  // 默认完成编译+链接全流程
- g++ hello.cpp -o hello.exe 但在编辑器里按"F5 运行"看结果   // 坑3：exe 未重新生成就跑旧程序，改了代码却见旧行为（结果错）
+ 每次改码后重新编译再运行                     // 流水线每次都要完整走一遍
```

**⑤ 典型应用**（自编练习 + 竞赛衔接）

- 自编练习（自编）：故意制造三种错误各一次——删一个分号（编译期语法错）、声明一个函数但从不定义也不调用换成调用（链接期 undefined reference）、写 `int a[3]; cin >> a[5];`（运行期越界）——记录三种错误各自的表现形式，建立"错误发生在哪个阶段"的条件反射。
- 竞赛衔接说明：绝大多数 OJ 与赛场（CCF-CSP、蓝桥杯）的评测本质都是"对源码执行这条流水线后，喂输入比对输出"。理解流水线，你才能看懂"编译错误=0 分但可重交、运行错误=RE、超时=TLE"这些反馈各自意味着哪个阶段出了问题——反馈定位能力在赛场上就是分数。

**⑥ 坑点与边界**

> **【易错】** 改了源码忘记重新编译就运行。后果：跑的是旧 exe，"我明明改了怎么没变"（结果错）。每次改码后必须重走流水线。

> **【易错】** 编译期错误与链接期错误不分。后果：见到 "undefined reference" 去改语法，越改越乱。语法错误在编译期报 `error:`，符号缺失在链接期报 `undefined reference to ...`，处置完全不同。

> **【注意】** -O2 是优化开关：它会重排、消除、内联代码，程序行为不变但**调试时断点会"乱跳"**。竞赛提交开 -O2 提速，本地调试可关（附录 B-4 实测用 -O2 编译通过，见 [[复杂度分析与递归]] 对常数因子的讨论）。

> [!example]-
> **边界数据集（流程类边界：以命令变体为数据集）**
> 1. 空输入：编译空文件（0 字节 .cpp）→ 链接器仍产出空 main 需至少一个 main，纯空文件报 undefined reference to `main`（预期：报链接错误而非崩溃）。
> 2. 单元素：只有一个 main 的文件 → 编译链接通过，运行无输出 exit 0（预期：骨架自足）。
> 3. 全相同：同一命令连跑两次 → 第二次覆盖同名 exe，行为一致（预期：幂等）。
> 4. 严格递增：逐步追加选项 `-std=c++17 -O2 -Wall` → 警告逐级增多，可执行性不变（预期：-Wall 暴露隐患）。
> 5. 严格递减：从完整命令逐个删选项 → 均能编译，仅标准与优化档位回落（预期：默认 = 老标准）。
> 6. 极值：单文件 10^5 行的表格初始化代码 → -O2 下编译时间明显变长但仍完成（预期：流水线不因规模失效，只是变慢）。

回扣开场：现在你知道一条 `g++ a.cpp -o a` 背后是四阶段流水线，也知道报错要按阶段分流。接下来解开流水线入口处那两行代码的真正含义。

### 3. 头文件与命名空间

前置依赖：知识点 2（预处理阶段对 #include 的处理）、知识点 1（扩充象限：名字空间）
后续衔接：（同批）《第一个C++程序》的 cout 第一课、（同批）《数据类型与内存表示》的 cin/cout 详解

**① 它解决什么问题**

模板前两行各管一件事：`#include <iostream>` 是**头文件机制**——把别人写好的声明"抄"进你的文件，让你能用 cout；`using namespace std;` 是**命名空间机制**——标准库的所有名字都住在叫 std 的"门牌"里，这句话让你免写 `std::` 前缀。解决什么问题：没有头文件，你每写一个程序都要手写一遍 cout 的声明；没有命名空间，一万人合作的代码里一万个 `max`、`count` 同名打架。命名空间正是 A 源 p5"扩充 C 语言"象限里的原话级新特性。

关键性质：`#include` 是**文本替换**（预处理期），命名空间是**名字的逻辑分区**（编译期）；引入 std 有三种粒度——全引入、点名引入、显式前缀（C 源《数据类型》p4-7 的三分法，本篇立骨架，详解在同批《数据类型与内存表示》）。

**② 直觉理解**

模型级类比：**头文件是"工具借用单"，命名空间是"小区门牌"**。`#include <iostream>` 相当于向物业登记借用公共工具房——登记后（预处理展开）工具的使用说明书（声明）就贴在你家门口，你能直接用，但工具本身（实现）还在物业仓库（标准库），最终由链接阶段送货上门。命名空间则是门牌：全城叫"张伟"的有几百个（名字冲突），`std::cout` 是"标准小区的 cout"，`using namespace std` 相当于办了张该小区的门禁卡——之后喊"cout"默认指这个小区的，直到你办别家小区的卡（using 别的 namespace）。

用具体场景跑一遍：你自己写了个函数 `void max(int a, int b)`，同时 `using namespace std;`——std 里也有 max。不冲突的场合能过，一旦参数恰好匹配，编译器就得在两个 max 之间猜（实际报二义性错误）。门牌的意义：`std::max` 与 `max` 从此各是各的。

**③ 原理与推导**

三种引入法的语义差异（C 源《数据类型》p5-7 推导）：

| 引入法 | 写法 | 引入范围 | 代价 |
|--------|------|---------|------|
| 全引入 | `using namespace std;` | std 全部名字 | 冲突风险最大 |
| 点名引入 | `using std::cout;` | 仅 cout、cin 等点名者 | 冲突风险小 |
| 显式前缀 | `std::cout` | 不引入，用时带门牌 | 无冲突，略啰嗦 |

**设计动机**：为什么标准库要整体塞进 std？推导——C 语言没有命名空间，库作者被迫给函数加前缀防撞（`strlen`、`strcpy` 的 str- 就是人肉命名空间）；C++ 有了语言级机制，就把整库装进 std 统一管理。为什么课件模板都用全引入？教学场景代码短、名字少，冲突概率低，换取书写最短；工程与赛场大代码里点名或前缀更稳。

`<iostream>` 尖括号与 `"myheader.h"` 双引号的区别：尖括号去系统目录找（标准库），双引号先在当前目录找（自己的头文件）——查找顺序不同，写错查找范围就报"找不到文件"。

**④ 代码演示**（最小可运行示例 + 执行追踪表）

三种引入法各写一份输出 666 的程序（自编示例）：

```cpp
// 写法一：全引入（课件模板标准形态）
#include <iostream>
using namespace std;              // 全引入：之后 cout 不带门牌
int main() { cout << 666 << endl; return 0; }
```

```cpp
// 写法二：点名引入 / 写法三：显式前缀（自编示例）
#include <iostream>
using std::cout;                  // 写法二：只点名 cout（endl 同理需点名）
using std::endl;
int main() { cout << 666 << endl; return 0; }
// 写法三：不写任何 using，每次带门牌：std::cout << 666 << std::endl;
```
**执行追踪表**（对写法一追踪"名字如何被找到"）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | `#include` 行 | 预处理 | 展开 iostream | cout 声明进翻译单元，住在 std 内 |
| 2 | using 行 | 编译期 | 打开 std 门牌 | std 全部名字进入可见集 |
| 3 | `cout << 666` | 编译期 | 无前缀查找 cout | 在可见集命中 std::cout |
| 4 | `<< endl` | 编译期 | 同上命中 endl | 输出 666 加换行 |

**错误写法对照**：

```diff
- #include <iostream>
- int main() { cout << 666; return 0; }              // 坑1：包含头文件但没引入 std——cout 未声明（编译错误 'cout' was not declared）
+ #include <iostream>
+ using namespace std;                                // 三种引入法任选其一
- #include <iostream>
- using namespace std;
- int max = 5; int main() { cout << max; }           // 坑2：全引入后自定义名字撞 std（此例恰好不炸），换成定义 max(int,int) 函数再调 max(1,2) 即报二义性（编译错误）
+ int myMax = 5;                                      // 全引入时给自定名字起独特名，或改用点名引入
- #include "iostream"                                // 坑3：标准库误用双引号——多数编译器能碰巧找到，但语义错，规范是尖括号（可移植性隐患）
+ #include <iostream>                                 // 标准库一律尖括号
```

**⑤ 典型应用**（自编练习 + 竞赛衔接）

- 自编练习（自编）：把写法一改出三种"崩法"各编译一次——删掉 include、删掉 using、把 cout 改成 std::cout 却删掉 using——记录三种报错信息的差异，下次见到即可秒判缺的是头文件还是命名空间。
- 竞赛衔接说明：竞赛模板几乎清一色写法一（全引入），理由是赛场代码短、追求录入速度；但 [[链表]]、[[栈与队列]] 等结构篇的手写代码若与 STL 同名（如自定义 queue），全引入会埋雷——本知识点的三分法就是那颗雷的排雷图。cin/cout 本体从《第一个C++程序》（同批）开始实操。

**⑥ 坑点与边界**

> **【易错】** 只 `#include <iostream>` 不引入 std 就用 cout。后果：`'cout' was not declared in this scope`（编译错误）。三选一：全引入、点名引入、显式前缀。

> **【易错】** 全引入 + 自定义名字与 std 撞名。后果：轻则二义性编译错误，重则（名字恰好能匹配）静默选错函数、答案错。自定义类型与函数加前缀或换名。

> **【注意】** `.h` 与无后缀头的区别：`<iostream>` 是 C++ 标准头（名字在 std 里），`<iostream.h>` 是前标准时代产物（名字全局裸奔），现代编译器已不提供——照抄老教材代码遇到 "no such file" 时先查这里。

> [!example]-
> **边界数据集（以"三种引入法 + 三种缺失"为数据集矩阵）**
> 1. 空输入：文件只有 include 无 main → 链接错 undefined reference to main（预期：错误在链接期）。
> 2. 单元素：include + using + 单句输出 → 通过（预期：三要素齐备即可运行）。
> 3. 全相同：三份引入法程序对同一输入输出完全一致（预期：引入法只改名字查找，不改行为）。
> 4. 严格递增：逐个点名引入 cout、endl、cin → 每加一行可用名字多一个（预期：增量验证三分法）。
> 5. 严格递减：从全引入逐步退到显式前缀 → 代码变长但行为不变（预期：等价性）。
> 6. 极值：同时 using namespace std 与自定义 namespace mine，两边各有一个同名 count 函数 → 不加限定调用即二义性错误（预期：门牌必须显式）。

回扣开场：模板前两行已完全解码——include 借声明，using 开门牌。最后一个知识点把赛场环境一次配好，让这套流程在你手里真正跑起来。

### 4. 竞赛环境配置

前置依赖：知识点 2（编译流程与 g++ 命令）、知识点 3（头文件与命名空间的报错识别）
后续衔接：（同批）《第一个C++程序》创建工程实操、全部后续篇的本地验证流程

**① 它解决什么问题**

会读代码不等于能跑代码——本知识点解决"从零到能在本地编译运行 C++"的落地问题：装什么（编译器套件）、怎么调（命令行参数）、赛场没 IDE 怎么办（notepad + 命令行）。属补充内容：章 2 素材仅存资源文件（附录 B-2），此处按竞赛通识与附录 B-4 实测补讲。关键性质：竞赛环境的最小集 = 编译器（MinGW-w64 的 g++）+ 任意文本编辑器；VS 是舒适但非必需的重型选项。

**② 直觉理解**

模型级类比：**IDE 是"集成厨房"，命令行是"一口锅走天下"**。VS 像全集成厨房：切菜（编辑）、开火（编译）、装盘（运行调试）一气呵成，代价是搬进赛场很难。命令行流派只有一口锅（g++），配上随身砧板（任意编辑器），走到哪烧到哪——赛场评测机恰好就是这一派。两条路线做的是同一桌菜（同一套四阶段流水线）。

用具体清单跑一遍（本机实测环境）：MinGW-w64 装在 `C:\mingw64` → g++ 实体在 `C:\mingw64\bin\g++.exe` → 把该目录加入 PATH 后任何目录敲 `g++ --version` 有响应 → 配置完成。四件套，缺一不可。

**③ 原理与推导**

竞赛环境两条铁律的推导。**铁律一：PATH 决定命令可达性**。终端敲 `g++` 时，系统按 PATH 环境变量逐目录搜索同名可执行文件——`C:\mingw64\bin` 不在 PATH 里，`g++` 就是"未识别的命令"；配 PATH 的本质是告诉系统去哪找锅。**铁律二：编译标准必须显式指定**。g++ 不带 `-std` 时按默认标准（通常偏旧）编译，`auto`、范围 for 等 C++11 后语法直接报错——竞赛题解默认 C++11 及以上，所以 `-std=c++17` 必须成为肌肉记忆（附录 B-4 全部实测命令带此参数）。

常用参数一览（为什么是这几个——设计动机：竞赛只关心"对、快、稳"三件事）：

| 参数 | 作用 | 竞赛场景 |
|------|------|---------|
| `-std=c++17` | 指定语言标准 | 题解语法基线（本工程 v3.1 口径） |
| `-O2` | 开二级优化 | 提速常数因子，评测机默认开 |
| `-Wall` | 打开常用警告 | 赛前自查隐患（未初始化、类型窄化） |
| `-o name` | 指定输出文件名 | 免去默认 a.exe 的混乱 |
| `-g` | 生成调试信息 | 本地调试用，提交不涉及 |

**④ 代码演示**（最小可运行示例 + 执行追踪表）

一份从建文件到看到输出的完整脚本（自编示例，命令行流派）：

```bash
# 竞赛最小工作流（在代码所在目录执行）
g++ -std=c++17 -O2 -Wall a.cpp -o a.exe    # 编译链接，-Wall 顺带查隐患
./a.exe < in.txt > out.txt                 # 喂输入文件、收输出文件（重定向）
fc out.txt expect.txt                      # Windows 下比对两文件（Git Bash 用 diff）
```

**执行追踪表**（对 `./a.exe < in.txt > out.txt` 的动作追踪）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | 系统找 g++ | PATH 逐目录搜索 | 命中 C:\mingw64\bin | 命令可达 |
| 2 | 四阶段流水线 | 编译+链接 | 产出 a.exe | 可执行就绪 |
| 3 | `< in.txt` | 标准输入重定向 | cin 读的是文件而非键盘 | 输入自动化 |
| 4 | `> out.txt` | 标准输出重定向 | cout 写文件而非屏幕 | 结果可留档 |
| 5 | fc/diff | 文件比对 | 逐行核对 | AC 或定位 WA |

**错误写法对照**：

```diff
- g++ a.cpp -o a.exe 且从未配置 PATH        // 坑1：'g++' 不是内部或外部命令（环境未就绪）
+ 把 C:\mingw64\bin 加入 PATH 后重开终端     // PATH 改动需新终端才生效
- g++ a.cpp -o a.exe 后直接把 a.cpp 拖给评测机   // 坑2：评测机要的是源码，本地 exe 是给自己看的；反之本地只交 exe 没意义（概念错位）
+ 交源码，exe 只用于本地验证                  // 两类文件各司其职
- g++ -std=c++98 a.cpp                       // 坑3：标准定太老，题解的 cin/vector/范围for 全报错（编译错误）
+ g++ -std=c++17 a.cpp                       // 与工程基线一致
```

**⑤ 典型应用**（自编练习 + 竞赛衔接）

- 自编练习（自编）：断网状态下，从新建空文件夹开始，仅用记事本与命令行完成"写一个输出自己名字的程序并跑通"，全程不碰任何 IDE——这条 10 分钟流程就是赛场环境的完整预演。
- 竞赛衔接说明：后续每一篇笔记的素材代码都按"知识点 4 的工作流"实测（附录 B-4 留痕）；掌握重定向比对后，你可以不依赖 OJ 自测边界数据集——⑥节的边界数据集就是为此设计的，本地跑通再提交，能挡掉大半 WA。

**⑥ 坑点与边界**

> **【易错】** 改了 PATH 不重开终端。后果：新变量对已开终端不生效，误判"配置失败"。重开终端再验证。

> **【易错】** 命令里源文件与 -o 顺序混乱导致把源码覆盖掉，如 `g++ -o a.cpp a.cpp`。后果：源文件被产物覆盖（不可逆）。固定顺序：`g++ 选项 源文件 -o 输出`。

> **【注意】** VS 与命令行双修时注意运行方式差异：VS 里"开始执行"会闪退的窗口，命令行运行天然可见输出；反过来 VS 工程默认子系统设置可能让命令行 exe 行为不同。赛场以评测机行为为准，本地验证以命令行流派为准。

> [!example]-
> **边界数据集（环境类边界：以配置变体为数据集）**
> 1. 空输入：PATH 无 mingw 目录时敲 g++ --version → 未识别命令（预期：定位到 PATH 缺失）。
> 2. 单元素：PATH 配置正确但目录下无 g++.exe → 同样报未识别（预期：区分"路径没配"与"文件没装"）。
> 3. 全相同：同一命令在 cmd 与 Git Bash 各跑一次 → 输出一致（预期：shell 无关性）。
> 4. 严格递增：参数从 -std 到 -std+-O2 到再加 -Wall → 逐级增强，均能出 exe（预期：参数正交可叠加）。
> 5. 严格递减：逐个去掉参数 → 仍可编译，仅标准/优化/警告回落（预期：最小命令 = g++ a.cpp）。
> 6. 极值：-O2 对 10^7 次循环的朴素计数程序提速实测（本机 g++ x64）→ 优化档耗时显著低于无优化档（预期：-O2 价值量化，实测数据留待学习者自行跑表记录）。

回扣开场：现在你能解决开场那个困境了——模板前两行已解码（用的是知识点 3 的结论），一条 `g++ -std=c++17 -O2` 让它跑起来（用的是知识点 2 的流水线与知识点 4 的参数）。环境就绪，下一篇正式写第一个程序。

## 四、总结与自测

### 核心内容（一页纸速览）

- **从 C 到 C++**：名字即定位（C 加加）；四象限——继承 C、改进 C（引用/const/内联取代宏）、面向对象（封装继承多态重载模板）、扩充 C（namespace、new/delete）；运行效率仅比汇编慢 10%-20%（A 源 p6）。
- **编译运行流程**：预处理（#include 文本展开）→ 编译（语法检查+翻译）→ 汇编（二进制目标文件）→ 链接（接标准库出 exe）；四阶段分工复用是大程序可维护的根基。
- **头文件与命名空间**：include 是借声明，实现由链接送货；std 是标准库门牌，引入三法——全引入（快但有冲突风险）/点名引入/显式前缀（稳）。
- **竞赛环境**：最小集 = g++（MinGW-w64）+ 任意编辑器；铁律两枚——PATH 决定命令可达、-std 必须显式；-O2 提速、-Wall 自查、重定向自动化比对。本篇为纯概念篇，语法实操从《第一个C++程序》（同批）开始。

## 五、语法糖对照表

| 语法 | 等价 C 写法 | 一句话用途 |
|------|------------|-----------|
| `#include <iostream>` | `#include <stdio.h>` | 引入输入输出声明 |
| `using namespace std;` | 每个名字前手写 `std::`（C 无此机制，等价于库前缀约定） | 免门牌前缀 |
| `cout << x << endl;` | `printf("%d\n", x);` | 流式输出，类型自动匹配 |
| `const double PI = 3.14;` | `#define PI 3.14` | 有类型的常量，可查错 |
| `std::cout`（显式前缀） | 库函数名全局直接可用（C 无命名空间） | 零冲突的保守写法 |
