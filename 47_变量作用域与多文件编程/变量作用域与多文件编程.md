## 一、为什么需要它

先碰一次壁：上一篇汉诺塔的 `static int count = 1` 跨调用累加（同批《函数》），你当时被要求"只需知道不会销毁"——现在必须还债：它凭什么不会销毁？再碰一堵更大的墙：code.cpp 素材里 isPrime、fibo、hanoi、sum 全挤在一个 200 行文件里；项目一旦长到几千行、几个人分工，"所有函数一个文件"就无法维护。11.2 多文件编程.pdf p4 给出原则："实现相同功能的代码应存储在一个文件中。"**碰壁的根源：单文件模型里既没有"变量能活多久"的显式控制，也没有"代码按功能分家"的机制。**

本篇讲 4 个知识点：局部与全局作用域、static 静态变量、头文件与声明定义分离、编译链接初步。顺序理由：作用域规则（1）是地基；static（2）把"作用域"与"生命周期"两个维度解耦；多文件（3）把声明/定义分离从单文件推广到文件之间；编译链接（4）解释多文件如何被装配成一个程序——前三节的知识在第四节各就各位。

## 二、知识点逐讲（每个知识点一节，共 4 节）

### 1. 局部与全局作用域：可见范围与存活时间

前置依赖：数据类型与内存表示（同批，栈区与静态区）、函数定义与参数传值（同批《函数》，栈帧）
后续衔接：本篇 ### 2. static 静态变量：作用域不动、生命周期拉满、本篇 ### 4. 编译链接初步：翻译单元与两阶段报错

**① 它解决什么问题**

11.1 变量作用域.pdf p4：变量在程序中都有一定的作用范围，称之为**作用域**。两条基本规则（p8、p10）：**函数内部声明的叫局部变量，作用域仅限函数内部**（函数参数、if/for 结构里的变量也都是局部变量）；**函数外部定义的叫全局变量，整个文件都有效**。配套素材 txt 的总结：局部变量"进入作用域时自动生成，离开作用域时自动消失"（默认 auto 存储类）；全局变量"生命期一直到程序的结束"。查一个变量是否可用是 $O(1)$ 的编译期判定——编译器按名字查找规则逐层向外找，不产生运行时代价。

**② 直觉理解**

模型级类比：**办公室的门牌与工牌**。作用域是"你能进哪些门"（可见性），生命周期是"你的工牌何时生效/作废"（存活时间）。局部变量是会议室里的白板——进门才能看见（作用域限函数），散会就擦掉（生命周期到函数结束）；全局变量是公司大堂的公告栏——所有部门都能看见（整个文件有效），从开门到关门一直在（程序全程）。

小数据推演（11.1 p8 的块作用域案例）：main 里 `{ int num = 100; cout << num; }`，出右大括号后那行注释掉的 `cout << num` 若放开就是编译错误——num 随块结束消亡。**同名覆盖规则**（p8 原话）：全局与局部同名时，"在函数内，局部变量会覆盖全局变量"——函数内看到的是局部的，全局那一份还在但被挡住。

**③ 原理与推导**

两个维度的严格区分：**作用域**（可见性）回答"在哪里能写这个名字"；**生命周期**（存续期）回答"这块内存在哪个时间段有效"。局部变量两维都小：作用域限块/函数，生命周期到出块（栈帧回收）；全局变量两维都大：整个文件可见、活到程序结束（存静态区，11.1 p12："静态存储区的变量在程序刚开始时完成初始化，是整个程序生命周期的唯一一次初始化"）。**为什么要把这两个概念拆开讲？** 因为 static 变量马上会给出"作用域小、生命周期大"的组合——两维正交，混为一谈就无法理解下一节。

全局变量的价值与代价：全局变量能免传参跨函数共享（11.1 p20-21 课堂练习用它数函数调用次数），但任何函数都能改它——状态不可控、复用性差，竞赛中全局数组是惯例（`int a[100005]` 开静态区不怕爆栈），全局计数器要克制。块作用域 `{}` 可主动收窄变量的可见范围（p8"使用 {} 可以限制变量的作用域"），让临时变量在用完即死的块里。

**④ 代码演示**

块一「核心代码」——块作用域、同名覆盖、全局计数（取自 11.1 pdf p8/p11/p20-21，自编整合，注明：自编示例，素材全角标点已修正，见 A-3 登记 2）：

```cpp
#include <iostream>
using namespace std;

int count = 0;                 // 全局：跨函数共享的调用计数（课堂练习 p20）
int num = 100;                 // 全局 num

void test() {
    cout << "test sees num = " << num << endl;   // 函数内无同名局部：看到全局
}
void shadow() {
    int num = 10;              // 局部 num：覆盖全局同名（p8 规则）
    cout << "shadow sees num = " << num << endl;   // 输出 10
    count++;                   // 修改全局 count
}

int main() {
    {
        int inner = 7;         // 块作用域：仅此大括号内可见
        cout << "inner = " << inner << endl;
    }
    // cout << inner;         // 错：inner 已消亡（放开即编译错误）
    test();                    // test sees num = 100
    shadow();                  // shadow sees num = 10（覆盖生效）
    cout << "num = " << num << endl;   // 仍是 100：覆盖只在 shadow 内部
    cout << "count = " << count << endl;   // 1：全局计数生效
    return 0;
}
```

块二「执行追踪表」（按 main 执行序，标注每步"谁可见"）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | 块 { int inner=7; } | 栈上临时块 | 打印 inner，出块销毁 | inner=7，随后不可见 |
| 2 | test() | 全局区 num=100 | 函数内查找 num：无局部同名 | 输出 test sees num = 100 |
| 3 | shadow() 进栈 | 新栈帧 num=10 | 名字查找命中局部，全局被覆盖 | 输出 shadow sees num = 10 |
| 4 | count++ | 全局区 count=0 | 读写全局 | count=1 |
| 5 | shadow 返回 | 栈帧销毁，局部 num 消亡 | 全局 num 未被触碰 | main 中 num 仍 100 |
| 6 | 输出 count | 全局区 | 读全局 | 输出 count = 1 |

块三「错误写法对照」：

```diff
- { int inner = 7; } cout << inner;   // 坑1：块外使用块内变量——inner 已销毁（编译错误，编译器兜底）
+ 变量的使用紧贴其定义的块内；需要块外使用就提升定义位置
- int count; void f() { int count = 0; count++; }   // 坑2：以为改的是全局计数，实际自增的是局部副本（答案错，静态单测必炸）
+ f() 内直接 count++ 不重新定义，或显式 ::count++   // 全局作用域解析符
- int mian() { ... }                  // 坑3：11.1 pdf p13 原文笔误 mian——链接器找不到程序入口（链接错误 undefined reference to WinMain/main）
+ int main()                          // 入口名拼写必须精确（A-3 登记 1）
```

**⑤ 典型应用**

- 课堂案例（11.1 pdf p20-21）：全局变量统计函数被调用次数——全局状态的最小用例（for 循环调 100 次，输出 100）。
- 素材 txt（全局和局部变量作用域及生命周期.txt）：全局/局部两维总结——正文知识点 1 的结论直接引自此文件与 pdf p8/p10/p12。
- 竞赛衔接：竞赛模板的全局约定——数组、并查集 fa、邻接表头全部开全局（静态区，不怕深递归爆栈），函数参数只传"变化的部分"（如 DFS 的当前节点编号）。竞赛衔接说明：全局数组默认清零（静态区初始化，p17"静态变量由编译器提供默认值 0"）——多组数据题必须记得每组重新清空，这是全局便利的另一面。

**⑥ 坑点与边界**

> **【易错】** 同名覆盖记反。后果：以为函数里读改的是全局，实际操作的是局部（答案错）。对策：函数内不与全局重名；必要时用 `::name` 显式指全局。

> **【易错】** 把"作用域大"与"生命周期长"混为一谈。后果：无法理解下一节 static——作用域与生命周期是两个独立维度。

> **【注意】** 全局变量在程序启动时一次性初始化（静态区）；`int a[100005];` 全局开就是全零，局部开则是随机值——同一行代码两种定义位置，行为完全不同。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：无输入的计数程序 → 循环 0 次，count=0（预期：输出 0，全局初始为零）。
> 2. 单元素：循环 1 次 → count=1（预期：最小样本计数）。
> 3. 全相同：100 次调用同一函数 → count=100（预期：与课堂练习一致）。
> 4. 严格递增：shadow 的局部 num 依次 10,20,30 → 每次都只影响函数内输出（预期：全局 num 恒 100）。
> 5. 严格递减：块内定义后再出块、再进同名新块 → 新块重新初始化（预期：两块互不相干）。
> 6. 极值：全局数组 `int a[1000000]`（4 MB）→ 静态区可容纳（预期：不爆栈；同尺寸局部开在栈上，深调用下栈溢出 RE——全局开数组的理由）。

回扣开场：作用域与生命周期两个维度拆清了。现在能回答汉诺塔伏笔的一半——"count 活得久"，另一半"为什么只能在那一个函数里用"就是 static 的专属设定。

### 2. static 静态变量：作用域不动、生命周期拉满

前置依赖：本篇 ### 1. 局部与全局作用域：可见范围与存活时间、数据类型与内存表示（同批，静态区）
后续衔接：本篇 ### 3. 头文件与声明定义分离：.h 放声明、.cpp 放定义（static 修饰全局变量/函数的隐藏含义）、C语言要点与内存管理（库内笔记，静态区的展开）

**① 它解决什么问题**

11.1 pdf p12 定义：**函数内定义的 static 变量，作用域只在其函数内，但生存周期为整个源程序**——"只可以在定义该变量的函数内进行使用，但是退出该函数后，该变量一直存在，但不可以进行使用"（原文直译了这对矛盾组合）。p17 补充：静态变量只初始化一次、直到程序结束；编译器给静态变量默认值 0。单次读写 $O(1)$；价值在于"免传参的函数私有记忆"——这就是《函数》篇 hanoi 的 `static int count` 跨调用累加而局部变量做不到的原因。

**② 直觉理解**

模型级类比：**带锁的私人抽屉**。static 局部变量是员工桌上一把带锁的私人抽屉：只有这个员工（函数）有钥匙（作用域不动），但抽屉在办公楼里常驻（生命周期拉满）——下班（函数返回）锁上，第二天上班（再次调用）拉开，里面的东西还在。普通局部变量是会议室白板（散会即擦），全局变量是大堂公告栏（人人可写）——static 抽屉恰好介于两者之间。

小数据推演（11.1 p17 的 v1/v2 案例，连调三次 func）：static v1 与局部 v2 都初始化为 0。第 1 次调用：v1++ 到 1、v2++ 到 1，输出 v1=1 v2=1；第 2 次：v2 重新初始化为 0 再 ++ 到 1，v1 没有"重新初始化"这回事、直接 ++ 到 2，输出 v1=2 v2=1；第 3 次输出 v1=3 v2=1。**v1 跨调用累积、v2 每次归零**——static 与 auto 的一字之差，行为天壤之别。

**③ 原理与推导**

static 的存储位置（p12）：静态存储区，"程序刚开始时就完成初始化，也是整个程序生命周期的唯一一次初始化"——首次执行到定义行时初始化，之后的函数进入不再初始化（p13 注释原话："首次进入函数时，num 初始化；后面再进入函数时，num 不会被初始化"）。**为什么 static 局部变量能"记得住"？** 它根本不住在栈帧里——函数栈帧随返回销毁，静态区不随函数进出变化；所谓"函数内的 static"只是把**名字的可见范围**限制在函数内，内存本体一直在静态区。这回答了设计动机：static 把《函数》篇追踪表里"栈帧销毁、num 消失"的环节整个绕开，同时不像全局变量那样敞开大门——名字查找仍从函数内部开始，函数外写这个名字直接编译错误。

11.1 p13 的静态案例（全角标点与 mian 拼写已修正，A-3 登记 1/2）值得逐行推演：全局 num=1，func 里 `static int num = 5; return num--;`。main 循环 `for(; num <= 5; num++)` 打印 `num << "---" << func()`——**全局 num 控制循环次数，静态 num 独立倒数**，两个同名 num 互不干扰（静态 num 的作用域锁在 func 内，全局 num 在 main 与 func 里各得其所——func 里静态局部覆盖全局，又是知识点 1 的覆盖规则）。

**④ 代码演示**

块一「核心代码」——static 计数与全局/静态同名对照（取自 11.1 pdf p17/p13 与同批《函数》hanoi，自编整合，注明：自编示例）：

```cpp
#include <iostream>
using namespace std;

int num = 1;                       // 全局 num（p13 案例）
int func() {
    static int num = 5;            // 静态 num：首次执行到此初始化为 5，此后不再初始化
    return num--;                  // 返回当前值再自减（后置 --）
}
void counter() {
    static int v1 = 0;             // 静态：跨调用累积（p17 案例）
    int v2 = 0;                    // 局部：每次归零
    v1++; v2++;
    cout << "v1=" << v1 << " v2=" << v2 << endl;
}

int main() {
    counter(); counter(); counter();   // v1=1 v2=1 / v1=2 v2=1 / v1=3 v2=1
    for (; num <= 5; num++)            // 全局 num 控制循环
        cout << num << "---" << func() << endl;   // 静态 num 独立倒数
    return 0;
}
```

块二「执行追踪表」（main 的 for 循环段，全局 num=1 起步、静态 num=5 起步）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | 全局 num=1 | 静态区：g_num=1, s_num=5 | 首次调用 func：静态 num 初始化 5 | 返回 5，s_num 变 4 |
| 2 | 输出 | 同上 | 打印 1---5，全局 num++ 到 2 | 第 1 行 |
| 3 | 全局 num=2 | s_num=4（不再初始化） | func 直接 num-- | 返回 4，s_num 变 3 |
| 4 | 依次推进 | s_num 持续减 | 2---4、3---3、4---2、5---1 | 第 2-5 行 |
| 5 | 全局 num=6 | s_num=0 | 6<=5 为假，循环结束 | 程序退出，静态区回收 |

块三「错误写法对照」：

```diff
- void f() { static int c = 0; c++; } // main 里写 c++   // 坑1：以为 static 变量全程序可用——作用域仍在函数内（编译错误）
+ static 的"长寿"不等于"可见"；要用就通过返回值或引用传出去
- void f() { static int c = 0; } void g() { static int c = 0; }   // 坑2：以为两个 c 是同一个——各自函数内各自的静态变量（答案错）
+ 跨函数共享记忆用全局变量或引用参数，static 只做"函数私有记忆"
- int f() { static int n = rand(); ... }   // 坑3：以为每次调用重新执行初始化行——初始化只发生一次（11.1 p12 原话），rand 只在首次调用执行
+ 需要"每次都跑"的语句放在初始化行之外
```

**⑤ 典型应用**

- 课堂案例（11.1 pdf p13）：全局/静态同名双 num——两维度正交的活教材（实测推演见④追踪表，程序化断言见附录 B-5）。
- 课堂案例（11.1 pdf p17）：v1/v2 三连调——static 与 auto 的行为分界。
- 竞赛衔接：《函数》篇 hanoi 的 `static int count`（跨调用计移动次数）是 static 在竞赛代码里最常见的用法；另一种是"只算一次的查找表"——`static bool inited = []{ ... }();` 一类懒初始化（延伸，非必需）。竞赛衔接说明：static 局部变量让函数从"纯函数"变成"有状态函数"，多测题里状态残留是隐形杀手——用前问一句"第二次调用时它还记得上次吗"。

**⑥ 坑点与边界**

> **【易错】** 以为 static 局部变量每次调用重新初始化。后果：计数器永远 1、缓存永远新鲜（答案错）。对策：初始化只在首次执行（p12 原话"唯一一次初始化"）。

> **【易错】** 把 static 当跨函数共享手段。后果：两个函数各自的 static 是两个变量（答案错）。对策：跨函数共享用全局或传引用；static 的定位是"函数私有 + 程序级寿命"。

> **【注意】** static 修饰全局变量与函数时含义变为"限制在本翻译单元内"（其他文件不可 extern 到它）——这是知识点 3、4 的伏笔，工程里用它避免命名冲突（延伸，非必需）。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：循环 0 次 → func 一次未被调用，静态 num 尚未初始化（预期：初始化随首次执行发生，"懒初始化"语义）。
> 2. 单元素：循环 1 次 → 输出 1---5（预期：静态 num 首次初始化为 5）。
> 3. 全相同：连调 counter 三次 → v1=1,2,3 而 v2 恒 1（预期：与④一致）。
> 4. 严格递增：循环到 5 → 静态 num 从 5 递减到 1（预期：两序列反向交错）。
> 5. 严格递减：num-- 改为 ++ 的变体 → 1---5, 2---6, 3---7 ...（预期：静态 num 递增不封顶，无边界检查）。
> 6. 极值：静态 num 自减 2^31 次后溢出为负（预期：int 回绕；计数器用 unsigned long long 或接受回绕）。

回扣开场：汉诺塔伏笔两清——count 住在静态区（活得久）、名字锁在 hanoi 函数里（看不见）。变量的一生规律齐了，接下来把这些规则搬到"多个文件"的尺度。

### 3. 头文件与声明定义分离：.h 与 .cpp 的分工

前置依赖：本篇 ### 1. 局部与全局作用域：可见范围与存活时间、函数定义与声明（同批《函数》，先声明后使用）
后续衔接：本篇 ### 4. 编译链接初步：翻译单元与两阶段报错、预处理命令（同批，#ifndef 的宏机制）

**① 它解决什么问题**

11.2 多文件编程.pdf p4：为方便分工与维护，"实现相同功能的代码应存储在一个文件中"——.h 头文件、.cpp 源文件（Windows 惯例）、.cc（Unix）。分工原则（p5 三件套）：**student.h 放函数声明（`void printInfo();`），student.cpp 放定义（#include 自己的头文件后实现），main.cpp #include "student.h" 后调用**。头文件的本质是"声明清单"：让每个使用方只看见签名、不必看见实现。一次 #include 是文本替换，预处理阶段 $O(文件大小)$ 完成，运行时零开销。

**② 直觉理解**

模型级类比：**菜单与后厨**。头文件是贴在门口的菜单——写清"有什么菜、什么价"（函数签名）；源文件是后厨——真正做菜的地方（函数定义）；顾客（main.cpp）看菜单点菜，不需要进后厨。菜单可以印多份发到每桌（被多个文件 #include），菜谱只有后厨一份——**这就是"声明可以重复出现，定义只能有一份"** 的形象版本。

小数据推演（11.2 p11 的 #ifndef 守卫流程）：第一次 #include "student.h" 时宏 _STU_ 未定义 → 定义它并展开头文件内容（三条声明生效）；第二次 #include（直接或经别的头文件间接）时 _STU_ 已定义 → 内容整段跳过。守卫让"菜单印多少份都不重叠"。

**③ 原理与推导**

为什么声明/定义必须分离（回收《函数》篇 p7-9 的伏笔）：编译器逐文件独立工作（见知识点 4 的翻译单元），编译 main.cpp 时它只认识本文件出现过（或 #include 进来）的名字——所以使用其他文件函数前必须把声明喂给它；而定义若在多个文件各写一份，链接阶段会出现"同一符号多个实体"，报 multiple definition。**为什么定义不能放进头文件？** 头文件会被多处 #include，每次包含等于把定义文本复制一份——除非是 inline 函数或类内定义（面向对象篇，同批），普通函数定义只许住在 .cpp 里。

防重复包含三法（11.2 p10-14，与素材 txt 完全一致）：1. **#ifndef/#define/#endif 宏守卫**——兼容性最好（C/C++ 通用），每次引入都要识别宏，效率一般；2. **#pragma once**——编译器直接记住文件只编一次，效率高，非标准但主流编译器全支持（VS2017 新建头文件自带）；3. **_Pragma("once")**——C99 的操作符版本，可与宏搭配。p14 给出工程实践："考虑到编译效率和可移植性，两者经常结合使用"——素材 student.h 正是这样：顶部 #pragma once + #ifndef _STU_ 双保险。`#include <>` 与 `#include ""` 的区别（p9）：尖括号只找编译器类库路径（标准头），双引号先找项目相对路径再退到标准目录（自定义头）。

**⑥ 坑点与边界**

> **【易错】** 头文件里写函数定义。后果：多处包含即 multiple definition（链接错误）。对策：.h 放声明 + 守卫，定义住 .cpp。

> **【易错】** 用尖括号包含自定义头文件。后果：编译器在系统路径里找不到（编译错误）。对策：自定义用双引号，标准库用尖括号。

### 4. 编译链接初步：翻译单元与两阶段报错

前置依赖：本篇 ### 3. 头文件与声明定义分离：.h 与 .cpp 的分工、预处理命令（同批，#include 的文本替换语义）
后续衔接：C语言要点与内存管理（库内笔记，内存布局总账）、面向对象编程（同批，类的声明定义分离同构）

**① 它解决什么问题**

多文件不是"把多个文件一起读一遍"：g++ 逐个文件独立翻译（每个 .cpp 是一个**翻译单元**），各自产出目标文件（.o/.obj），最后由**链接器**把对得上的符号拼成一个可执行程序。报错因此分两类：**编译错误**（某翻译单元内部语法/类型不过）与**链接错误**（各单元都编译通过了，但符号对不上——undefined reference / multiple definition）。分清两类错误能立刻定位问题在"文件内"还是"文件之间"——这是多文件开发的第一诊断技能。

**② 直觉理解**

模型级类比：**流水线装配**。每个 .cpp 是一个独立车间：车间内部装配（编译）出半成品（.o），车间之间只按"订单符号"交接；总装线（链接器）拿着 main 车间的订单（printInfo() 调用）去仓库找成品——找不到就贴条"undefined reference"，找到两件一样的就报"multiple definition"。车间质检（编译）管单个车间，总装线（链接）管车间之间。

小数据推演（附录 B-5 实测两例）：例 1，`g++ student.cpp main.cpp -o main` 通过，运行输出三行。例 2，只编译 main.cpp（不带上 student.cpp）：编译阶段无恙（声明满足编译器），链接阶段报 `undefined reference to 'printInfo()'`——**声明骗过了编译器，骗不过链接器**。

**③ 原理与推导**

两阶段的分工推导：编译器的工作边界是单文件 + 被 #include 展开的全部文本（所以"翻译单元"= .cpp 内容 + 所有头文件展开）。函数调用在编译期只需"名字与签名匹配"（知识点 3 的声明已足够）；函数实体在哪个目标文件，编译器不管、链接器管——链接器收集所有目标文件的符号表，把"未定义的引用"与"别处导出的定义"配对。**为什么声明与定义分离能行得通？** 因为两个阶段的信息需求不同：编译要"长得对"（签名），链接要"找得到"（实体）——分离恰好让两个阶段各取所需。

extern 的角色（11.1 p19；素材 txt："如果在一个文件中使用 extern 关键字来声明另一个文件中存在的全局变量，那么这个文件可以使用这个数据"）：`extern int g;` 是声明（"别处有这个变量"），不含初始化器；**注意 `extern int v1 = 0;` 带初始化器时 extern 被忽略、变成了定义**（A-3 登记 5）——跨文件共享全局变量的标准写法是"一个 .cpp 里定义，其他文件里 extern 声明"（或把 extern 声明收进头文件）。static 反向封锁：static 全局变量/函数不出本翻译单元（知识点 2⑥ 的伏笔兑现）。

**④ 代码演示**

块一「核心代码」——两阶段编译实测脚本（命令行演示，非源码；基于素材三件套，注明：自编示例）：

```text
# 阶段一：分开编译（各车间独立质检）
g++ -std=c++17 -c student.cpp -o student.o      # 只编译不链接
g++ -std=c++17 -c main.cpp    -o main.o         # 只编译不链接
#   两步都成功：声明已满足编译器

# 阶段二：链接（总装）
g++ student.o main.o -o main                    # 符号配对成功，生成可执行文件
./main
#   student info
#   student name
#   20

# 反例实测（附录 B-5）：漏掉 student.cpp 直接连
g++ main.cpp -o broken
#   /usr/bin/ld: undefined reference to `printInfo()'
#   链接错误：声明骗过编译器，骗不过链接器
```

块二「执行追踪表」（错误分类诊断流程，以三件套为例）：

| 步骤 | 当前阶段 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | 编译 main.cpp | 只有声明（头文件展开后） | 检查 printInfo() 调用的签名 | 通过：名字与签名匹配 |
| 2 | 编译 student.cpp | 有完整定义 | 生成三个函数实体 | 通过：本单元自洽 |
| 3 | 链接 | 两个 .o 的符号表 | main.o 找 printInfo 定义 | 在 student.o 配对成功 |
| 4 | 反例：缺 student.cpp | 只有 main.o | 订单无人认领 | 报 undefined reference（链接错误） |
| 5 | 反例：两文件都定义 printInfo | 两个 .o 各有一份 | 同名符号争位 | 报 multiple definition（链接错误） |

块三「错误写法对照」：

```diff
- g++ main.cpp -o main            # 坑1：多文件工程只编译主文件——编译全过、链接报 undefined reference（附录 B-5 实测）
+ g++ student.cpp main.cpp -o main   # 所有 .cpp 一起喂给链接器
- // a.cpp 与 b.cpp 都写 int g_value = 0;（各自想初始化共享计数）   # 坑2：双份定义，链接报 multiple definition
+ a.cpp 写 int g_value = 0; b.cpp 写 extern int g_value;   # 一处定义、多处 extern 声明（素材 txt 口径）
- extern int v1 = 0;              # 坑3：extern 带初始化器，extern 被忽略变成定义（11.1 p19 原文写法，A-3 登记 5）
+ 声明写 extern int v1; 定义写 int v1 = 0; 两件事分开
```

**⑤ 典型应用**

- 课堂案例（11.2 pdf p4-5 + student 三件套）：版权/保密场景只发 .h + 二进制——声明先行让使用方无需源码即可编译调用。
- 素材 txt（说一说避免重复引用的方法有哪些？.txt）：三种防重复包含方法清单——11.2 p10-14 的速记版，知识点 3③ 已展开。
- 竞赛衔接：赛场上"链接错误"最常见于两类——忘把新写的 .cpp 加入编译命令、函数名拼写与声明不一致（符号对不上）。竞赛衔接说明：本地调试多文件时固定一条编译命令（如 `g++ -std=c++17 -O2 *.cpp -o a`），把装配环节从心智负担变成肌肉记忆。

**⑥ 坑点与边界**

> **【易错】** 把链接错误当编译错误修。后果：在报错文件里反复找"语法问题"而找不到（报错行根本没有语法错）。对策：见 undefined reference / multiple definition 先查"文件之间"——定义缺失、拼写不一致、重复定义。

> **【易错】** extern 带初始化器。后果：本想声明却成了定义（A-3 登记 5），多文件下诱发 multiple definition。

> **【注意】** 各 .cpp 的 using namespace std 只影响本翻译单元（知识点 1 的文件级推论）；头文件里写 using namespace 是污染源（把命名空间选择强加给所有包含者），工程规范是头文件里写全 std:: 前缀（延伸，非必需）。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：main.cpp 为空文件（素材 Test001.cpp 即此状态）→ 编译链接通过，无输出（预期：空翻译单元合法）。
> 2. 单元素：只链接一个 .cpp 且自包含（含 main）→ 通过（预期：单文件工程是两阶段的退化情形）。
> 3. 全相同：同一 .cpp 编译两次得到两个 .o 一起链接 → main.o 与 main.o 符号全冲突，multiple definition（预期：重复装配必炸）。
> 4. 严格递增：工程从 1 个 .cpp 逐个加到 4 个 → 每加一个须同时进编译命令（预期：漏一个即 undefined reference，实测案例见④）。
> 5. 严格递减：删 student.cpp 里 getAge 的定义而 main 仍调用 → 链接报 undefined reference to `getAge()`（预期：与④例 2 同理）。

## 四、总结与自测

### 核心内容（一页纸速览）

- **作用域与生命周期**：局部变量两维都小（限块/函数、出块即亡）；全局变量两维都大（全文件可见、活到程序结束）；同名时局部覆盖全局。
- **static 局部变量**：作用域不动（锁在函数内）、生命周期拉满（静态区、唯一一次初始化、默认零值）——函数私有记忆。
- **多文件分工**：.h 放声明（菜单）、.cpp 放定义（后厨）；防重复包含三法（#ifndef / #pragma once / _Pragma），工程常双保险；尖括号找标准库、双引号先找项目。
- **编译链接**：每个 .cpp 是独立翻译单元；编译管"文件内对不对"，链接管"文件之间配不配对"；undefined reference = 有声明无定义，multiple definition = 定义重复。
- **extern 与 static 对偶**：extern 声明跨文件可见，static 修饰封锁在本翻译单元。

### 前置概念清单

- 函数（同批）：定义/声明分离、栈帧、static count 伏笔——本篇在文件尺度重演同一机制。
- 数据类型与内存表示（同批）：栈区/静态区——生命周期差异的物理载体。
- 预处理命令（同批）：#include 文本替换、#ifndef 宏守卫——多文件的预处理机制（待产出，先文字锚定）。
