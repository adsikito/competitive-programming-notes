## 一、为什么需要它

构造一个新手 100% 会撞上的场景：你按上篇配好环境，写下第一个程序，满心欢喜按下编译——屏幕吐出一整屏英文：`error: expected ';' before '}'`。你逐字读，一个词都认识，连起来不知道它在说哪一行出了什么事。这是每个学 C++ 的人的第一堵墙：**程序还谈不上对不对，先得能编译通过**；而读懂报错的前提是知道每行骨架代码各自在干什么。

本篇讲 4 个知识点：main 函数与程序骨架、cout 输出第一课、注释与代码规范、编译错误初体验。顺序理由：骨架（知识点 1）是一切的地基，输出（知识点 2）是程序与外界对话的唯一窗口，注释与规范（知识点 3）决定两周后你自己还读不读得懂，编译错误（知识点 4）则把前面三个知识点的每个部件拆开重装一遍——拆过的人不再怕报错。

## 二、知识点逐讲（每个知识点一节，共 4 节）

### 1. main 函数与程序骨架

前置依赖：[[C语言要点与内存管理]]（C 函数定义、返回值）、（同批）《C++简介与开发环境》的编译流程
后续衔接：（同批）《数据类型与内存表示》的 cin 输入、[[复杂度分析与递归]]（main 只是普通函数，可被理解成入口约定）

**① 它解决什么问题**

B 源 p10 给出每份 C++ 程序的标准开场：

```cpp
#include <iostream>
using namespace std;
int main()
{
    cout << "hello world!";
    return 0;
}
```

四行各司其职：`#include <iostream>` 引入输入输出声明；`using namespace std;` 打开标准门牌（两行的机制在上篇已解码）；`int main()` 是**程序的入口**（B 源 p13 原话），操作系统启动你的程序时从它开始执行；`return 0` 是**程序的出口**（B 源 p14），返回 0 表示程序正常运行结束。解决什么问题：所有可执行程序都必须有唯一入口——没有 main，链接器直接罢工（上篇边界数据集实测过 `undefined reference to main`）。

关键性质：main 的返回类型是 int；返回值 0 传给操作系统，非 0 通常表示异常退出；每个指令以分号结束（B 源 p15）。复杂度视角：骨架本身零开销——它只是约定，不产生任何运行时代价，这就是为什么设计成"约定"而不是"运行时查找"（设计动机：入口在编译期就确定，运行期零成本）。

**② 直觉理解**

模型级类比：**main 是剧场正门，return 0 是散场登记**。观众（操作系统）永远从正门进来；演出（程序语句）按剧本顺序进行；散场时门口登记簿写"一切正常"（return 0），写"着火了"（非 0 值）剧场保安（系统）就会记一笔事故。至于正门里有多少个演员（函数、变量），观众不关心从哪个门进——入口永远唯一。

用具体数字跑一遍：Test002.cpp 的 main 里有 4 条输出语句，执行顺序严格自上而下——先输出不带换行的 `hello world!`，再输出带 `\n` 的、再输出带 endl 的，最后 return 0。附录 B-4 实测输出恰好三行相连，顺序零意外。

**③ 原理与推导**

为什么入口必须是 `int main()` 而不是别的？推导：进程结束时操作系统要读取一个退出码来判断成败，退出码是整数——所以 main 返回 int；`return 0` 的 0 按 C/C++ 惯例表示"无错误"（成功），非 0 由程序自定义含义。main 花括号 `{ }` 圈出函数体（B 源 p13"函数后面{ }"），里面每条语句必须以 `;` 结束——分号是语句的边界符，编译器靠它切分语句，这就是漏分号必报错的机制根源（知识点 4 展开）。

执行顺序推导：从 main 第一句开始，逐句执行，直到 return 或右花括号——没有循环与跳转时就是线性流。多条 `cout` 语句按书写顺序输出（Test002 实测），因为流插入是顺序副作用。

**④ 代码演示**

取自源文件 Test002.cpp（改动：仅将原文 4 行输出语句原样保留并加注释；文件本身逐行未动）：

```cpp
#include <iostream>          // 引入输入输出声明（预处理期文本展开）

using namespace std;         // 打开 std 门牌，之后免写 std::

int main() {                 // 入口：操作系统从这里开始
    cout << "hello world!";          // 第 1 句：无换行
    cout << "hello world\n";         // 第 2 句：\n 换行（C 写法 printf("hello world\n");）
    cout << "hello world" << endl;   // 第 3 句：endl 换行并清空缓冲区
    return 0;                        // 出口：0 = 正常结束
}
```

实测输出（附录 B-4）：`hello world!hello world`（第 1、2 句连排后换行）+ `hello world`——第 1 句没有换行符，所以第 2 句的内容紧贴在叹号后面。

**执行追踪表**（n=4 句的小数据，逐句追踪）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | `#include` 行 | 预处理期 | 展开 iostream | cout 声明可见 |
| 2 | main 第一句 | 缓冲区空 | 送入 "hello world!" | 屏幕暂无输出 |
| 3 | main 第二句 | 缓冲区 12 字符 | 送入 "hello world\n" | 刷出连排两串后换行 |
| 4 | main 第三句 | 缓冲区空 | endl 刷出 "hello world" | 再出一行并清缓冲 |
| 5 | return 0 | 栈帧回收 | 退出码 0 交系统 | 程序结束 |

**错误写法对照**：

```diff
- int main() { cout << "hi" return 0; }      // 坑1：字符串后漏分号——编译器读到 return 才发现语句没断开（error: expected ';'）
+ int main() { cout << "hi"; return 0; }     // 每条指令以分号结束（B 源 p15）
- int Main() { ... }                          // 坑2：入口写成 Main——大小写敏感，链接器找不到 main（undefined reference to 'main'）
+ int main() { ... }                          // 入口名必须全小写
- void main() { ... }                         // 坑3：无返回值版——部分编译器容忍，但标准要求 int；评测机按标准走（可移植性隐患）
+ int main() { ... return 0; }                // 标准形态，退出码可控
```

**⑤ 典型应用**（无对应 OJ 题，给自编练习与竞赛衔接）

- 自编练习（自编）：只允许改动 main 函数体，把 Test002.cpp 改成输出一首五言绝句（两行，每行一句加换行），要求：第一行用 `\n` 结尾、第二行用 endl 结尾，并用执行追踪表预测输出再实测对照。
- 竞赛衔接说明：竞赛代码的 main 骨架固定不变，变的只是函数体——后续所有篇目（[[栈与队列]]、[[二叉树结构篇]] 等）的代码都在这个骨架里生长。main 的返回值在竞赛里几乎总是 0；一旦程序崩溃（RE），操作系统收到的就是非 0 退出码——这也是评测机区分 AC 与 RE 的依据之一。

**⑥ 坑点与边界**

> **【易错】** 语句漏分号。后果：报错行往往在**下一行**（编译器读完下一行才发现上一句没结束），新手按报错行号找不到错误——看到 expected ';' 就往报错行的上一行找。

> **【易错】** main 写成 Main 或 MAIN。后果：链接期 undefined reference。C++ 大小写敏感，入口名是法律条文，不能变通。

> **【注意】** `return 0;` 在 main 里可省略（标准规定 main 隐式返回 0），但竞赛里建议显式写——与函数习惯一致，避免在非 main 函数里误以为也可省略（非 main 的 int 函数无返回值是未定义行为）。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：main 体为空 `{}` → 编译通过，无输出，exit 0（预期：骨架自足）。
> 2. 单元素：只有一条 `cout << "A";` → 输出 A 无换行（预期：缓冲区内容在退出时刷出）。
> 3. 全相同：三条完全相同的 `cout << "A\n";` → 输出三行 AAA 各占一行（预期：顺序执行）。
> 4. 严格递增：输出语句逐条加，从 1 条到 5 条 → 输出按书写顺序连排（预期：线性流）。
> 5. 严格递减：从 5 条删到 0 条 → 始终可编译（预期：删减不破坏骨架）。
> 6. 极值：main 里连写 10^5 条 `cout << 'a';` → 编译稍慢、输出 10 万字符，正常退出（预期：语句数量不改变骨架语义，仅变慢）。

回扣开场：现在你知道第一堵墙的砖是怎么砌的了——expected ';' 说的是分号边界，undefined reference 说的是入口约定。骨架立好，下一节让程序开口说话。

### 2. cout 输出第一课

前置依赖：知识点 1（骨架与 using namespace std）、（同批）《C++简介与开发环境》知识点 3（std 三种引入法）
后续衔接：（同批）《数据类型与内存表示》的 cin 详解与类型化输出、[[排序]] 等后续篇的调试输出

**① 它解决什么问题**

cout 是**输出流对象**（B 源 p15 原话），`<<` 是**流插入运算符**——把右侧数据"插"进 cout 这条通往屏幕的流水线。解决什么问题：C 的 printf 需要人肉维护格式符（`%d`、`%f`、`%c` 一旦和实参类型不匹配就是未定义行为）；cout 按数据的实际类型自动选择输出方式，格式符错误这一大类 bug 从机制上消失。这就是设计动机：**把类型匹配的责任从程序员转移给编译器**。

关键性质：cout 可以一次连续输出任意多个数据（B 源 p15：`cout << 数据1 << 数据2 << 数据3;`）；`endl`（end of line）输出一个换行并**清空输出缓冲区**；换行也可以用 `"\n"`，区别只在是否清缓冲（B 源 p15）。复杂度视角：单次流插入 O(1)，一行的输出成本与字符数成正比——竞赛中输出量巨大时，`\n` 比 endl 略快（少做缓冲刷新），属于常数级优化。

**② 直觉理解**

模型级类比：**cout 是传送带，<< 是把货放上传送带的动作，缓冲区是传送带末端的打包台**。货物（字符）放上去并不立刻到用户手里，先在打包台攒一批，攒够或收到"立刻发货"指令（endl / 缓冲区满）才整批发出。攒批发货比一件一送便宜得多——这就是缓冲区存在的原因（与屏幕逐字符通信太慢，攒批摊薄通信开销）。

用具体数字跑一遍（Test002 实测）：第 1 句 `cout << "hello world!";` 攒了 12 个字符不发货；第 2 句再放 12 个（含 `\n`）——`\n` 只是普通字符，不触发发货，但程序退出时打包台清仓，你才看见连排的 `hello world!hello world`；第 3 句用 endl，当场发货一行。三句话跑出了缓冲区的全部行为。

**③ 原理与推导**

链式输出为什么能一直接下去？推导：`cout << "a" << "b"` 按从左到右结合——先算 `cout << "a"`，这个表达式的返回值**还是 cout 自己**，于是继续被 `<< "b"` 消费。这个"返回自身"的设计（设计动机二）让一条语句串起任意多个数据，也是 B 源 p15 语法式的由来。endl 与 `\n` 的推导：`\n` 是单个换行字符，随数据流走；endl = 输出 `\n` + 强制刷新缓冲区两件事。什么时候必须 endl？交互式程序需要在读输入前把提示打出来（否则提示压在缓冲区里用户看不见）；竞赛的对拍输出文件场景两者等价，用 `\n` 更快。

C 等价写法锚点：`cout << 666 << endl;` 等价于 `printf("%d\n", 666);`——printf 用格式串声明类型，cout 让编译器查类型；`cout << "a" << "b"` 等价于 `printf("%s%s", "a", "b")`。

**④ 代码演示**

在 Test002 基础上的链式与变量输出（自编示例）：

```cpp
#include <iostream>
using namespace std;
int main() {
    int x = 666;
    cout << "x = " << x << endl;        // 链式：字符串与变量混排（等价 printf("x = %d\n", x);）
    cout << 'A' << '\t' << 3.14 << endl;  // 字符、制表符、小数各按自身类型输出
    cout << "a" << "b" << "\n";          // 普通字符串直接连排
    return 0;
}
```

实测输出：`x = 666` / `A    3.14` / `ab`（附录 B-4 同环境实测验证链式顺序）。

**执行追踪表**（对 `cout << "x = " << x << endl;`，x=666）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | `<< "x = "` | 缓冲区 0 字符 | 插入 4 字符 | 缓冲区 4 字符 |
| 2 | `<< x` | 缓冲区 4 字符 | 666 按整型转 3 字符插入 | 缓冲区 7 字符 |
| 3 | `<< endl` | 缓冲区 7 字符 | 插入换行并刷新 | 屏幕出 `x = 666`，缓冲区清空 |

**错误写法对照**：

```diff
- cout << "x = " x << endl;          // 坑1：漏第二个 <<——两个输出项之间没有运算符衔接（编译错误）
+ cout << "x = " << x << endl;       // 每个数据项前都要一个 <<
- cout << endl << "结果："; cin >> x;   // 坑2（交互场景）：提示语用 endl 在前看似没问题，但若写成提示后不刷新（用 \n 又不 endl），提示压在缓冲区，用户先被卡在输入（交互异常）
+ cout << "请输入："; cin >> x;        // 提示后紧接输入的交互场景用 endl 刷新（竞赛文件 IO 不受影响）
- cout << "结果\n"; cout << "继续";   // 坑3（示意）：把 endl 当成"必须的句号"每句都加——功能对但大输出量下频繁刷新拖慢速度（常数级 TLE 风险）
+ cout << "结果\n" << "继续";          // 纯文件输出用 \n，退出/结束前统一刷新即可
```

**⑤ 典型应用**（无对应 OJ 题，给自编练习与竞赛衔接）

- 自编练习（自编）：用一条链式 cout 输出九九乘法表的一行 `3*4=12`（其中 3、4、12 都是变量，不得写死字面量），预测输出后实测——练"字符串与变量交替插入"的节奏感。
- 竞赛衔接说明：竞赛程序的核心输出手段就是 cout（或 printf，二者可混用但别混风格）。数据量大时（如输出 10^6 行），endl 的逐行刷新与 `\n` 的攒批刷新差距可达数倍——先学 endl 理解机制，赛场养成 `\n` 习惯。cin 与 cout 是一对（B 源 p8-9 的 cin 语法在同批《数据类型与内存表示》详解），本篇先立输出侧。

**⑥ 坑点与边界**

> **【易错】** 两个输出项之间漏 `<<`。后果：编译错误。链式输出的每个数据项前都必须有流插入符，`cout << "a" "b"` 虽因字符串字面量拼接碰巧合法，但对变量必炸。

> **【易错】** 认为输出语句执行完屏幕就一定有字。后果：交互程序里提示语"消失"，卡在输入。缓冲区未刷新时输出不可见——需要即时可见处用 endl。

> **【注意】** `\n` 写在字符（`'\n'`）与字符串（`"\n"`）中都可以，但别与 `/n` 混淆——方向写反是高频手误，报错为未声明标识符或输出成多余内容。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：无任何 cout → 无输出，exit 0（预期：不崩）。
> 2. 单元素：`cout << 'A';` → 输出单字符 A 无换行（预期：退出时刷出）。
> 3. 全相同：`cout << "AB" << "AB" << "AB";` → 输出 ABABAB（预期：连排）。
> 4. 严格递增：链式从 1 项加到 6 项 → 输出顺序与插入顺序严格一致（预期：从左到右）。
> 5. 严格递减：从长链删到单项 → 仍正确（预期：链长无关正确性）。
> 6. 极值：一次链式插入 10^5 个数字 → 输出完整且顺序无错（预期：缓冲攒批不影响结果，仅影响发货时机）。

回扣开场：现在你的程序能说话了——cout 管说，缓冲区管什么时候说。会输出还得会"写给人看的代码"，下一节补上注释与规范。

### 3. 注释与代码规范

前置依赖：知识点 1（骨架）、知识点 2（输出语句——注释常用于临时移除输出调试）
后续衔接：（同批）《数据类型与内存表示》的变量命名规则（本篇立纪律，那边给规则表）、全部后续篇的代码书写

**① 它解决什么问题**

注释是用自然语言解释代码功能的文字，编译器完全忽略它（C 源《数据类型》p17 原话级内容：注释"在必要时，还可以将代码临时移除，是调试程序的好帮手"）。解决什么问题：第一，两周后的你看不懂两周前的代码——注释是写给未来的自己的信；第二，调试时把可疑语句"注释掉"而不是删除，能快速对比行为差异。C 源给出经验值：合理的注释应占源代码 1/3 左右。本知识点素材在《数据类型》p17（同批下一篇的素材文件），本篇按用户知识路径前置立骨架，标注：资料未覆盖于本篇源文件，属补充。

关键性质：两种形态——单行注释 `//`（行注释）与多行注释 `/* */`（块注释）；注释在预处理阶段被剥离，对运行速度零影响（为什么注释不影响性能——设计动机：注释是给人看的元信息，编译产物里根本没有它）。

**② 直觉理解**

模型级类比：**注释是菜谱里的"小贴士"**。"翻炒 30 秒"是步骤（代码），"锅要烧到冒烟再下料，不然粘锅"是小贴士（注释）——不看贴士也能照做，但第一次做大概率翻车。代码同理：`while (l < r)` 是步骤，`// 循环不变量：答案在 [l, r] 内` 是贴士——没有它，两周后你自己就是那个翻车的人。

用具体行为跑一遍：把 Test002 的第 2 句输出用 `//` 注释掉，重编译，实测输出少了对应一行——注释即"临时移除"，这正是 C 源 p17 说的调试用法。

**③ 原理与推导**

两种注释的适用边界推导：`//` 从出现处生效到**本行末尾**，适合逐行解释与快速禁用单句；`/* */` 从 `/*` 到最近的 `*/`，可跨行，适合成段说明与文件头。块注释**不可嵌套**——内部再出现 `*/` 就提前闭合，剩余文字被当代码，报一串莫名其妙的错误；所以禁用大段代码时要么每行加 `//`，要么用编辑器的注释开关。推导注释纪律：注释写"为什么"而非"是什么"——`i++; // i 加一` 是废话，`i++; // 跳过已处理的哨兵位` 是信息。

规范三则（竞赛场景裁剪）：命名见名知意（`cnt` 表计数、`fa` 表父亲——并查集篇的 [[并查集与种类并查集]] 沿用此约定）；缩进一层四空格或一个 Tab，花括号换行风格全篇统一；一行一条语句——`a = 1; b = 2;` 挤一行在调试时单步跳不出，注释掉也连坐。

**④ 代码演示**

注释三种用法的最小演示（自编示例）：

```cpp
#include <iostream>
using namespace std;
/* 文件头：hello 注释演示
   用途：练注释三用法 */
int main() {
    int cnt = 0;                 // 计数器：统计输出次数（写"为什么"，不写"是什么"）
    // cout << "debug: old version\n";   // 调试：临时移除旧输出，不删除
    cout << "answer = " << cnt << endl;
    return 0;
}
```

实测：块注释与行注释均被剥离，输出 `answer = 0`；被注释的调试行不产生任何输出（附录 B-4）。

**执行追踪表**（预处理阶段对注释的处理追踪）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | `/* 文件头... */` | 预处理扫描 | 整块剥离 | 翻译单元中消失 |
| 2 | `// 计数器...` | 预处理扫描 | 剥到行尾 | 该行剩 `int cnt = 0;` |
| 3 | `// cout...` 调试行 | 预处理扫描 | 整行剥离 | 语句不进入编译 |
| 4 | 编译期 | 无注释纯净代码 | 正常编译 | 行为与无注释版完全一致 |

**错误写法对照**：

```diff
- /* 注释一 /* 嵌套注释二 */ 还算注释吗 */     // 坑1：块注释嵌套——第一个 */ 提前闭合，剩余文字被当代码（编译错误）
- // 单行注释续行 \
- 以为还在注释里                               // 坑2：行尾反斜杠续行会把下一行并进注释——可读性灾难（隐蔽 bug 温床）
+ 每行独立用 //，不玩续行                       // 注释永远成对、成行、显式
- int a=1,b=2; if(a) {b++;} cout<<b;          // 坑3：无缩进无空格多语句挤行——报错定位难，两周后自己都读不懂（维护成本爆炸）
+ int a = 1, b = 2;                            // 一行一事，缩进分层
+ if (a) { b++; }
+ cout << b << endl;
```

**⑤ 典型应用**（无对应 OJ 题，给自编练习与竞赛衔接）

- 自编练习（自编）：把你知识点 2⑤ 的乘法表程序加上三处注释——一处文件头块注释、一处行尾"为什么"注释、一处注释掉的调试输出——然后故意在块注释里嵌套一个 `*/`，实测编译报错并读懂报错文本。
- 竞赛衔接说明：赛场代码通常不加长注释（时间紧），但**调试输出注释切换**是赛场最常用的排错手段：写好调试 `cerr`/cout 后成对注释，提交前统一禁用。变量命名规范在竞赛里的价值是防手滑——全局 `cnt` 与局部 `cnt` 撞名这类 bug，一半靠命名纪律预防（规则表见同批《数据类型与内存表示》知识点 1）。

**⑥ 坑点与边界**

> **【易错】** 块注释嵌套。后果：第一个 `*/` 提前闭合，其余内容被当代码，报错位置离真实错误很远。禁用成段代码用行注释或编辑器批量注释。

> **【易错】** 注释掉调试输出却忘了恢复/删除就提交。后果：竞赛输出多出调试行，整题 WA——提交前全文搜索注释行，或用宏开关统一管理。

> **【注意】** 中英文输入法的分号、引号差异（`；` 与 `;`、`"` 与 `"`）是新手第一大错源——知识点 4 展开实测；注释里用中文没问题，**代码区**必须半角。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：全文件只有注释与 main 骨架 → 编译通过无输出（预期：注释零副作用）。
> 2. 单元素：仅一行 `//` 注释 → 可编译（预期：剥离干净）。
> 3. 全相同：同一行注释复制 10 遍 → 可编译（预期：注释数量无关行为）。
> 4. 严格递增：注释行数从 0 加到 6 → 输出恒不变（预期：纯元信息）。
> 5. 严格递减：把成段块注释逐步缩短 → 到只剩 `/**/` 空注释仍合法（预期：空块注释合法）。
> 6. 极值：注释里写 10 万字符 → 编译产物与性能零变化（预期：预处理剥离彻底）。

### 4. 编译错误初体验

前置依赖：知识点 1（骨架——错误都发生在骨架部件上）、知识点 2（cout 语法）、上篇编译四阶段（错误按阶段分流）
后续衔接：（同批）《数据类型与内存表示》的类型错误、全部后续篇的调试前置课

**① 它解决什么问题**

解决"报错恐慌"：第一次见到满屏英文报错的正确反应不是慌，而是分流——**错误发生在哪个阶段、报错指向哪一行、修哪一处**。本知识点把新手最高频的三类首错（漏分号、漏引号、中文标点）逐一亲手制造、观察报错文本、定位修复。标注：本篇源文件无报错实验内容，属补充；所有报错文本为附录 B-4 实测原文（g++ MinGW-w64），非编造。

关键性质：编译错误的三个观察维度——阶段（编译期/链接期）、行号（真实行/滞后行）、关键词（expected / was not declared / stray）。掌握三维分流后，90% 的首错 30 秒内可修。

**② 直觉理解**

模型级类比：**编译器是极端较真的海关**。你申报的每一句代码它逐字查验；漏分号就像申报单没写句读，海关不猜你的意思，只在"读不下去的那一行"盖章（报错行可能滞后于出错行）；中文标点像护照上的伪印——肉眼看着一样，机器一验就拒（stray '\uff1b'）。海关不会说谎也不会猜：**它报什么就是什么，但报的位置要你自己折算**。

用具体错误跑一遍（附录 B-4 实测记录，逐条复现）：删除 Test002 第 2 句的分号后编译，g++ 报 `error: expected ';' before 'cout'`——指向的是**下一句** cout，不是漏分号那行；把 `"hello"` 的引号写成中文 `"hello"`，报一串 `stray` 开头的错误；漏写 `#include <iostream>` 直接用 cout，报 `'cout' was not declared in this scope`（上篇实测过）。三种报错三种关键词，分流表见④。

**③ 原理与推导**

为什么漏分号的报错行号会滞后？推导：编译器的语法分析读到 `;` 才认定语句结束——漏写分号时，它继续把下一行当成当前语句的延续，直到读到无法拼进当前语句的记号（比如下一个 `cout` 或 `}`）才在**那个记号处**报错。所以 expected ';' 的正确排查方向是报错行及其**上一行**。为什么中文标点报 stray？推导：中文分号是 Unicode 字符 U+FF1B，编译器的词法分析器不认识它，逐字节报告 stray（走失字符）——关键词 stray 就是"这里有我不认识的字节"。

三维分流表（实测归纳）：

| 关键词 | 阶段 | 典型原因 | 修复 |
|--------|------|---------|------|
| expected ';' | 编译期 | 漏分号 | 报错行及其上一行补分号 |
| stray '\x...' | 编译期 | 中文标点/全角字符 | 切换半角输入法重写该处 |
| was not declared | 编译期 | 漏 include / 名字拼错 / 漏 using | 对照报错名逐项检查 |

**④ 代码演示**

三错误的制造与修复脚本（自编示例，每段单独编译观察报错，修复行已注）：

```cpp
// 实验一：漏分号（自编示例）
#include <iostream>
using namespace std;
int main() {
    cout << "a"        // 错：句尾无分号——报 error: expected ';' before 'return'（滞后到下一句）
    return 0;
}
// 修复：cout << "a";  —— 记住向报错行的上一行找

// 实验二：中文标点
// cout << "a"；        // 错：中文分号 U+FF1B——报 stray '\377' 系列字节错误
// 修复：cout << "a";  —— 半角分号

// 实验三：漏 include
// int main() { cout << "a" << endl; return 0; }   // 错：无 iostream——报 'cout' was not declared in this scope
// 修复：文件首补 #include <iostream>（using 也不能少，见上篇知识点 3）
```

**执行追踪表**（实验一的编译器视角，n=3 行代码）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | `cout << "a"` | 语句解析中 | 读完字符串，未遇分号 | 继续吞下一记号 |
| 2 | `return` | 语句解析中 | return 无法拼进输出语句 | 在此报 expected ';' |
| 3 | 修复后 `cout << "a";` | 语句闭合 | 顺利进入 return 解析 | 编译通过 |

**错误写法对照**（排查动作本身的对错）：

```diff
- 见 expected ';' 就改报错那一行              // 坑1：修错位置——真正缺分号处在报错行上一行（语法分析滞后机制）
+ 检查报错行及上一行的句尾分号                 // 滞后规律定向排查
- 报错一多就全删重写                          // 坑2：放弃读报错——g++ 默认只报第一处，修一处重编译，错误数逐次递减
+ 从第一条 error 开始逐个修，修一条编译一次    // 报错是按序暴露的瀑布
- 中文报错环境里凭感觉改                      // 坑3（示意）：不看 stray 的十六进制码——中文标点与半角形近难辨
+ 见 stray 就查该行的非 ASCII 字符            // 编辑器开"显示不可见字符"辅助
```

**⑤ 典型应用**（无对应 OJ 题，给自编练习与竞赛衔接）

- 自编练习（自编）：限时 5 分钟——将一份含 3 处埋错（漏分号、中文引号、漏 include）的程序编译修通，要求每处先说出预计关键词再编译验证；正确率与耗时长于 5 分钟则回④重读分流表。
- 竞赛衔接说明：赛场每分每秒都值分，编译错误的修复速度直接换算成做题量；三维分流表（关键词/阶段/行号）练熟后，首错平均 30 秒修复。链接期错误（undefined reference）在竞赛代码中的最大来源是漏写 main 或函数名拼错——上篇知识点 2 已给机制，此处不重复。类型相关的编译错误（如浮点取余）在《运算符与表达式》（同批）实测展开。

**⑥ 坑点与边界**

> **【易错】** 只盯着报错行号修。后果：越改越乱。记住两条滞后规律——expected 系列向上一行找、stray 系列就在本行。

> **【易错】** 一次改十几处再编译。后果：新错误与旧修复混在一起，无法归因。修一条编译一次，让瀑布按序收敛。

> **【注意】** 编译器报错的行号以预处理后的翻译单元为准，`#include` 展开不改变你的行号，但**宏展开**会让行号漂移——新手阶段不写宏即可避开（竞赛禁用复杂宏是纪律不是教条）。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：main 体为空 → 零错误编译（预期：基线存在）。
> 2. 单元素：仅一处漏分号 → 恰一条 error（预期：报错数 = 1）。
> 3. 全相同：同一处错误复制 3 份 → 逐条报出，修一处减一条（预期：瀑布递减）。
> 4. 严格递增：错误从 1 处加到 4 处 → 报错按出现顺序暴露，第一条总是靠前者（预期：从上往下修）。
> 5. 严格递减：从 4 错逐个修到 0 → 每次编译错误数严格递减（预期：归因清晰）。
> 6. 极值：一行 10^4 条语句挤一行再漏分号 → 报错行号正确但定位困难（预期：一行一句的规范价值实测）。

## 四、总结与自测

### 核心内容（一页纸速览）

- **程序骨架四件套**：include 引声明、using 开门牌、int main() 是唯一入口、return 0 是正常出口（B 源 p10-14）；骨架零运行时开销。
- **cout**：输出流对象，<< 流插入；链式原理是"表达式返回自身"；endl = 换行 + 刷缓冲区，`\n` 只换行；缓冲区是攒批发货的打包台（B 源 p15，Test002 实测三句行为）。
- **注释**：// 行注释、/* */ 块注释、不可嵌套；注释预处理期剥离，零性能影响；合理注释约占源码 1/3（C 源 p17）；写"为什么"不写"是什么"。
- **编译错误三维分流**：expected ';' 滞后向上一行、stray 查中文标点、was not declared 查 include/using/拼写；修一条编译一次。
- 语法细节的 C 等价锚点集中在《五、语法糖对照表》，变量与命名规则表在同批《数据类型与内存表示》。

| `cout << "a" << "b";` | `printf("%s%s", "a", "b");` | 链式连续输出 |
| `// 注释` | 同（C99 起支持；C89 仅 /* */） | 行注释 |
| `/* 注释 */` | 同 | 块注释 |
