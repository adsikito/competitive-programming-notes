## 一、为什么需要它

先看课件开场代码（21 异常处理.pdf p4）：

```cpp
int num1 = 100, num2 = 0, num3 = 0;
num3 = num1 / num2;        // 整数除零：运行时崩溃
```

整数除以零，程序当场终止——崩溃点在 main 里还好，若藏在第 20 层函数调用深处，错误现场离你能检查的地方隔了 19 层。异常处理给出的答案是：**出错的深层函数只负责"喊一声"（throw），处理权沿调用链逐层上浮，直到愿意接手的那一层（catch）**——课件作业答案原话："异常的引发和处理不必在同一函数中"。

但本篇定位要先说破（任务指定）：**算法竞赛几乎不用异常处理**——数组开够、边界检查才是正道，本篇按"延伸、读得懂即可"的深度讲（知识点 4 专述立场）。讲 4 个知识点：try/throw/catch 机制、自定义异常、栈展开、竞赛立场与惯例对比。

## 二、知识点逐讲（每个知识点一节，共 4 节）

### 1. try/throw/catch：一次控制权转移

前置依赖：[[函数]]（调用栈、返回值）、[[面向对象编程]]（读得懂类语法即可）
后续衔接：[[#2. 自定义异常与类型匹配：exception 基类与 enum 异常]]、[[#3. 栈展开：异常穿过的每一层都收拾干净]]

**① 它解决什么问题**

异常是"运行时抛出的事件或对象"，处理它的目标是错误发生后程序仍能体面收尾（p5 原话）。三个关键字分工（p6）：**throw** 在出错处抛出一个值（异常对象）；**try** 把可能出错的"保护代码"圈起来；**catch** 按类型接住抛出的值并处理。性质总账：throw 的操作数可以是任意表达式，其类型决定异常类型；一个 try 后可跟多个 catch 按类型分发；`catch(...)` 三点是万能兜底（p14/p16）。**复杂度**：不抛异常时 try/catch 几乎零成本，抛出时控制权跳跃的代价与穿透层数成正比——所以它管"罕见事故"，不管"日常分支"。

**② 直觉理解**

模型级类比：**公司事故上报**。一线员工发现事故不自己修，"throw 一张事故单"就撂手；单子沿着汇报线自动上浮，每一层只有写了"我能处理这类单子"（catch 匹配类型）的经理才会接单；一直没人接，单子顶到 CEO——程序终止。

用具体数字推演（p10-p16 的 div 案例）：`div(50, 0)`。第一步，无检查版：double 除零**不崩溃**，输出 `inf`（infinity，浮点阶码溢出的表示值，p10 课件注释）——注意这已经是错的，但程序没有喊疼。第二步，函数内加 `if (b == 0) throw "Division by zero condition!";`（p12 原式）：只抛不捕，程序异常终止（p13）——喊了没人接还是不行。第三步，调用方包上 try 并写 `catch (const char* msg) { cerr << msg << endl; }`（p16）：消息打印，main 继续跑到 return，程序正常结束（p15"程序可以正常运行结束了"）。三步递进，实测复现（附录 B-5）。

**③ 原理与推导**

控制流推导：throw 执行的瞬间，当前函数的剩余语句**全部跳过**（实测：throw 后的赋值语句不会执行，附录 B-5 第 8 组）；控制权带着异常对象沿调用链向上找最近的、类型匹配的 catch；找到则整个 try 块内 throw 之后的代码同样作废，从 catch 块继续；找不到则进程终止。**为什么 catch 按类型匹配而不是按值**：因为调用链上不同层关心的"事故种类"不同——下标越界、内存不足是不同的单子，类型就是单子的分类标签；这也解释了为什么一个 try 可以挂多个 catch，按声明顺序从上到下试（p9）。

设计动机：为什么不学 C 的返回错误码，要在语言里造这套机制？课件作业答案（p33）：底层函数专注具体业务，"上层调用者可以在适当的位置设计对不同类型异常的处理"——错误处理代码从主逻辑里剥离出去，主逻辑不再被 if 检查淹没。

**④ 代码演示**

**块一·核心代码**（取自课堂代码 mycode.cpp 的 test01 相关段；改动：仅摘录并保留注释说明，类名拼写修正见 A-3 登记 2）：

```cpp
#include <iostream>
#include <exception>
using namespace std;                  // C 等价：std::cerr 写全称
double mydiv(double v1, double v2) {
    if (v2 == 0) {
        throw "divsion by zero condition";   // 抛：字符串字面量，类型 const char*
    }
    return v1 / v2;                          // 除数非零才走到这
}
class MyException : public exception {       // 自定义异常（知识点 2 展开）
public:
    const char* what() const throw() { return "my test exception"; }
};
int main() {
    int num1 = 200, num2 = 0;
    try {                                    // 保护代码区
        cout << mydiv(num1, num2) << endl;   // 若抛出，本行之后的 try 内代码全部跳过
    }
    catch (const char* msg) {                // 按类型接：const char*
        cerr << msg << endl;                 // cerr：标准错误流（C 等价 fprintf(stderr,...)）
    }
    cout << "main 继续执行" << endl;          // 程序恢复常态，正常走到 return
    return 0;
}
```

实测：输出 `divsion by zero condition` 与 `main 继续执行`，退出码 0（附录 B-5）。

**块二·执行追踪表**（mydiv(200, 0) 全程）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | 调用 mydiv(200,0) | 栈：main、mydiv | 进入函数 | v2==0 成立 |
| 2 | throw 字面量 | mydiv 剩余代码跳过 | 控制权上浮 | 携带 const char* |
| 3 | 匹配 catch | 回到 main 的 try | 类型 const char* 匹配 | 进入 catch 块 |
| 4 | cerr 输出 | 异常已接住 | 打印消息 | 输出错误文本 |
| 5 | catch 结束 | 栈恢复 | 落到 try/catch 之后 | cout 正常执行，return 0 |

**块三·错误写法对照**：

```diff
- double mydiv(double v1, double v2) { return v1 / v2; }   // 坑1：整数版除零直接崩溃（p4），浮点版静默得 inf（p10）——两头都是错
+ if (v2 == 0) throw "Division by zero condition!";        // 出口前先设防（p12 原式）
- try { cout << mydiv(a, b) << endl; }                     // 坑2：只 try 不 catch（或只 throw 不 try）→ 编译通过、运行时程序异常终止（p13 原话"只抛出，不捕获，程序无法正常结束"）
+ try { ... } catch (const char* msg) { ... }              // 抛与接必须配套
- catch (const char msg) { ... }                           // 坑3：漏了 *，类型是 char，与抛出的 const char* 不匹配 → 接不住，继续上浮终止
+ catch (const char* msg) { ... }                          // 类型一字不差地匹配
```

**⑤ 典型应用**

- 素材案例（p10-p16 div 案例）：除零从崩溃到 inf 到 throw/catch 的三步改造——本知识点主线即此。
- 素材作业（p32-33）：什么叫异常处理、机制优点——答案即③的设计动机引用，标准答案在 p33。
- 迁移题（自编）：写 `int parseAge(string s)`，s 非纯数字时 `throw "not a number"`，main 里 try/catch 打印消息。建议先独立做，再对照题解：结构与 mydiv 完全同构，只换校验条件。

**⑥ 坑点与边界**

> **【易错】** 以为浮点除零会抛异常——不会（p10 实测输出 inf/nan 而非异常，nan 来自 -1 开方这类未定义操作）；异常只在你显式 throw 时存在。

> **【易错】** catch 的类型与 throw 的类型不一致（④对照坑 3）——编译不报错，运行时接不住，一路浮到顶直接终止，且没有任何提示。

> **【注意】** `catch(...)` 能接任何类型但拿不到异常对象（三点不声明变量），只适合"最后兜底记录一条"的场景；放前面会截胡所有后续 catch。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：不适用：机制不涉输入流程（预期：不涉及）。
> 2. 单元素：try 里只有一条语句且抛出 → 该语句后无残留，直接进 catch（预期：控制流干净）。
> 3. 全相同：连续三次调用都会 throw 的函数、各自包 try → 三次各自进 catch，互不影响（预期：每次 try 独立）。
> 4. 严格递增：三层嵌套 try（外抛内接 / 内抛外接）→ 就近匹配原则（预期：最近的可接 catch 优先）。
> 5. 严格递减：catch 链从具体到抽象排列 → 逐个试类型（预期：第一个匹配者赢，其余跳过）。
> 6. 极值：throw 抛 42（int）、抛 "str"（const char*）、抛对象——三种类型三张单子，catch 各接各的；全不接 → terminate 终止（预期：类型标签机制的分发实测，附录 B-5 第 5、6 组）。

回扣开场：现在你能解决"深层函数出错、main 里收尾"的问题了——throw 喊单、catch 接单（③的控制流结论）。但抛出的如果是个"类别"而不只是一句话，怎么建自己的单子类型？下一节。

### 2. 自定义异常与类型匹配：exception 基类与 enum 异常

前置依赖：[[#1. try/throw/catch：一次控制权转移]]、[[面向对象编程]]（public 继承与虚函数，读得懂即可）
后续衔接：[[#3. 栈展开：异常穿过的每一层都收拾干净]]、[[#4. 竞赛立场与错误处理惯例对比（延伸）]]

**① 它解决什么问题**

throw 一个字符串只有一句话的信息量，接方也无法按"事故类别"分发。标准库的解法（p5/p7）：所有标准异常派生自 `std::exception`，定义在 `<exception>`，按父子层次组织；**自定义异常 = 继承 exception 并重写 what()**（p17 原话）。what() 是 exception 提供的公共方法，返回异常原因。另一路轻量做法（练习题 p19-22）：直接 throw 一个**枚举值**当异常类型——underflow、overflow 各是一类。关键性质：catch(exception&) 用引用接住整棵异常家族树（多态分发，[[面向对象编程]] 知识点 3 的 virtual 在此处兑现）。

**② 直觉理解**

模型级类比：**标准化事故单**。上一节的字符串是"便签"；继承 exception 是"用公司统一模板填单"——单据格式（what() 接口）固定，各部门（各异常类）填各自的内容；接单的经理只看"是不是本公司单据"（catch(exception&)），读内容时调 what()，不用关心具体是哪个部门的单子。

用具体数字跑一遍（p18 原案例）：`add(200, 200)`，v1=200 大于 0，构造 MyException 对象并 throw。main 的 `catch (exception& e)` 接住——MyException 是 exception 的子类，引用绑定成立；`e.what()` 返回 "my test exception"。实测输出一致（附录 B-5 第 4 组）。

**③ 原理与推导**

两条路线的推导：**类路线**——`class MyException : public exception` 加 `const char* what() const throw()` 覆盖基类版本；捕获端写基类引用 `catch (exception& e)`，靠继承关系"宽接"，靠 what() 虚分发"细读"。**枚举路线**（练习题）——`enum index { underflow, overflow }`，函数内 `if (index < 0) throw underflow;`，捕获端 `catch (index e)` 后用 if 分辨是哪一类（p19-22）。**设计动机**：枚举路线为什么在练习题里可行？因为异常类型本身就是分发标签，枚举恰是最小的类型集合；类路线的信息容量更大（能带数据成员），扩展时不用改捕获签名——工程里用类路线，轻量教学场景用枚举路线。

**④ 代码演示**

**块一·核心代码**（取自课堂代码 mycode.cpp 的 test02 段；改动：enum 名由 index 改为 index_t 以避开与函数形参同名冲突，逻辑逐行原样；原练习题代码的 A[i] 笔误见 A-3 登记 1）：

```cpp
#include <iostream>
using namespace std;
enum index_t { underflow, overflow };   // 素材原为 enum index；两类异常：下标过小 / 过大
int array_index(int* arr, int n, int index) {
    if (index < 0)   throw underflow;   // 下标小于 0：抛枚举值
    if (index > n-1) throw overflow;    // 下标大于最大下标：抛另一枚举值
    return arr[index];                  // 合法下标：正常取值
}
int main() {
    int* arr = new int[5];
    for (int i = 0; i < 5; i++) arr[i] = i + 11;   // 元素为 11..15
    try {
        cout << array_index(arr, 5, 2) << endl;    // 13：正常路径
        cout << array_index(arr, 5, 100) << endl;  // 抛 overflow，本行输出不执行
    }
    catch (index_t e) {                            // 按枚举类型接
        if (e == underflow) cout << "下标太小了" << endl;
        else if (e == overflow) cout << "下标太大了" << endl;
    }
    delete[] arr;
    return 0;
}
```

实测：先输出 13，再输出 `下标太大了`（附录 B-5）。

**块二·执行追踪表**（array_index(arr, 5, 100) 越界分支）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | array_index(...,100) | arr 已装 11..15 | 100 < 0 不成立 | 走下一个判断 |
| 2 | index > n-1 | 100 > 4 成立 | throw overflow | 抛出枚举值 |
| 3 | try 块 | 第二个 cout 作废 | 上浮找 catch(index_t) | 类型匹配 |
| 4 | catch 块 | e == overflow | 走 else if 分支 | 输出 下标太大了 |
| 5 | catch 结束 | delete[] 归位 | 程序正常结束 | 退出码 0 |

**块三·错误写法对照**：

```diff
- int arr[5]; ... array_index(arr, 5, 100);   // 坑1（对照真实事故）：不设防直接下标 100 → 未定义行为，读出垃圾值或崩溃
+ if (index > n-1) throw overflow;            // 先检查再取值（练习题的设计正意）
- catch (exception e) { ... }                 // 坑2：按值接异常对象 → 发生对象切片，派生类部分被切掉，what() 可能调不到派生版
+ catch (exception& e) { ... }                // 引用接，保留多态（p18 原式即引用）
- if (index > n-1) throw overflow; return arr[index]; if (index < 0) throw underflow;   // 坑3（示意）：检查顺序颠倒 → 负下标先被 arr[index] 吃掉
+ 先判 underflow 再判 overflow，最后才取值   // 检查必须全部先于取值
```

**⑤ 典型应用**

- 素材练习（p19-22）：数组取元素，下标越界抛 underflow/overflow——本知识点枚举路线的主线；PDF 版代码有一处 `A[i]` 笔误，mycode.cpp 为可运行修正版（A-3 登记 1）。
- 素材案例（p17-18）：MyException 继承 exception + what()——类路线主线。
- 迁移题（自编）：写 `class NegativeError : public exception`，`int mySqrt(int x)` 在 x 小于 0 时抛它，main 里 catch(exception&) 输出 what()。建议先独立做，再对照题解：结构即 p17-18 原案例的换题版。

**⑥ 坑点与边界**

> **【易错】** catch 按值接异常对象（④对照坑 2）——对象切片吞掉派生类信息；异常捕获一律用引用。

> **【注意】** catch 匹配是"第一个类型匹配者赢"，不是"最精确者赢"——把 `catch(...)` 或宽类型 catch 放在窄类型前面，窄类型永远轮不到（就近顺序规则）。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：不适用（预期：不涉及）。
> 2. 单元素：array_index(arr, 5, 4) → 返回 arr[4]=15，恰好等于最大合法下标（预期：边界值 n-1 合法，n 越界）。
> 3. 全相同：连续调用同一合法下标 → 每次都正常返回（预期：无状态残留）。
> 4. 严格递增：下标 -1, 0, 2, 4, 5 → 依次抛 underflow、13、15、抛 overflow（预期：两类异常与合法值交错出现）。
> 5. 严格递减：下标 4, 2, 0, -1 → 15、13、11、抛 underflow（预期：对称验证）。
> 6. 极值：index=2147483647 → index > n-1 成立，抛 overflow，不越界访问（预期：防御先于访问，极值也是"一类单子"）。

回扣开场：现在你能建自己的异常类型了——枚举管"分几类"，exception 子类管"带信息的多态单据"（③两条路线）。但异常抛出后，半路上那些已经构造好的局部对象怎么办？下一节。

### 3. 栈展开：异常穿过的每一层都收拾干净

前置依赖：[[#1. try/throw/catch：一次控制权转移]]、[[函数]]（调用栈）
后续衔接：[[#4. 竞赛立场与错误处理惯例对比（延伸）]]

**① 它解决什么问题**

throw 发生在第 5 层函数，catch 写在第 1 层——中间 4 层函数的**局部对象还活着**，谁来销毁？答案是**栈展开**（stack unwinding）：控制权沿调用链上浮时，每一层里已构造完成的局部对象按构造的逆序自动析构。性质：栈展开只在异常抛出时发生（正常 return 也逐层析构，但那是另一条路径）；析构顺序可靠、与构造严格相反。一句话直觉（按任务要求控制深度）：**异常像退房——不收拾自己的房间直接走是不行的，走廊上每层都自动打扫一遍**。

**② 直觉理解**

用具体数字推演：main 调 middle，middle 里造了局部对象 g 后调 mydiv，mydiv 抛异常。顺序：mydiv 的栈帧先拆（它没对象）；middle 拆帧前析构 g；然后才轮到 main 的 catch 接住。实测：析构计数恰为 1 次（附录 B-5 第 6 组）；无异常路径同样析构 1 次（第 7 组）——**栈展开不额外制造析构，只是把"该走的清理"在异常路径上也执行**。

**③ 原理与推导**

推导"为什么必须展开"：C++ 的对象生命周期绑定栈帧，栈帧不拆、析构不跑，堆资源（对象内部 new 的内存）就漏了。异常路径若跳过析构，每次出错都是一次内存泄漏——所以语言规定展开是异常语义的一部分。**设计动机**：这套机制的配套纪律是"清理工作交给析构函数，不要散落在代码里"（RAII 思想，标注：延伸名词，只取含义）——析构是唯一保证在异常路径上也会执行的代码，把 delete 写进析构才安全。

**④ 代码演示**

**块一·核心代码**（自编示例，演示栈展开的观测方法）：

```cpp
#include <iostream>
using namespace std;
int dtor_count = 0;              // 析构观测计数器
struct Guard {
    ~Guard() { dtor_count++; }   // 析构时计数加一
};
double mydiv(double a, double b) {
    if (b == 0) throw "zero";    // 第 3 层：抛出
    return a / b;
}
int middle(double a, double b) {
    Guard g;                     // 第 2 层：局部对象，异常穿过时必被析构
    return mydiv(a, b);          // 异常从这里继续上浮
}
int main() {
    dtor_count = 0;
    try { middle(1, 0); }        // 异常路径：middle 展开时 ~Guard 执行
    catch (const char*) { }
    cout << dtor_count << endl;  // 输出 1：栈展开确实析构了局部对象
    return 0;
}
```

**块二·执行追踪表**（middle(1, 0) 的异常路径）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | main 调 middle | 栈：main、middle | middle 构造 g | dtor_count=0 |
| 2 | middle 调 mydiv | 栈：main、middle、mydiv | b==0 | throw "zero" |
| 3 | mydiv 帧拆除 | 栈：main、middle | 无局部对象 | 继续上浮 |
| 4 | middle 帧拆除前 | 展开进行中 | 析构 g | dtor_count=1 |
| 5 | 回到 main | catch 匹配 const char* | 接住 | 输出 1 |

**块三·错误写法对照**：

```diff
- int middle(int a, int b) {
-     int* p = new int[100];
-     return mydiv(a, b);        // 坑1：抛异常时 p 指向的内存没人 delete → 每次出错泄漏 400 字节
-     delete[] p;                // 坑2（连带）：delete 放在 return 之后，正常路径也永远执行不到
- }
+ 用局部对象包住资源：struct Arr { int* p; ~Arr(){ delete[] p; } } —— 析构在正常与异常两条路径上都会执行
- catch (...) { throw; }        // 坑3（示意）： catch 里 rethrow 前若吞掉半截清理逻辑，语义混乱
+ 空 catch 只用于"确定无事可做"的兜底；要继续上抛就写独立语句 throw;
```

**⑤ 典型应用**

- 迁移题（自编）：给④的 Guard 加构造计数，验证"构造 1 次、析构 1 次、异常路径无重复析构"。建议先独立做，再对照题解：加一个 ctor_count 对称观测即可。
- 竞赛衔接：竞赛代码几乎不写需要栈展开保护的资源管理（没有手工 new/delete 配对的传统是第一道防线），但**读工程代码与面试**必考这个概念；STL 容器的析构就是 RAII 的标准实现。
- 素材关联（登记说明）：同课件 p23-30 的嵌套类与局部类属类语法范畴，已在 [[面向对象编程]] 同批覆盖，本篇不重复（附录 B-2）。

**⑥ 坑点与边界**

> **【易错】** 资源释放写在 return 之后或依赖每条路径手工调用（④对照坑 1、2）——异常路径必漏。清理进析构函数，让栈展开代劳。

> **【注意】** 栈展开过程中再抛异常（析构函数里 throw）会直接 terminate——析构函数里不要抛异常，这是标准的铁律。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：不适用（预期：不涉及）。
> 2. 单元素：单层函数内 throw 且 catch 就在同函数 try 里 → 无中间层，展开距离最短（预期：局部对象仍析构）。
> 3. 全相同：三层函数都各有 Guard → 展开时析构 3 次、逆序（预期：每层一次）。
> 4. 严格递增：嵌套 1、2、3 层 → dtor_count 依次 1、2、3（预期：与层数线性）。
> 5. 严格递减：同上逆序观测 → 析构顺序与构造严格相反（预期：栈式生灭）。
> 6. 极值：异常穿过 1000 层函数 → 每层析构各一次，无泄漏但深度递归有栈溢出风险（预期：展开本身不崩，层数受栈深限制）。

回扣开场：现在你知道异常路上的每层都自动收拾（③的展开规则）——机制层面讲完了。最后一节回答竞赛立场：这一整套，赛场上用不用。

### 4. 竞赛立场与错误处理惯例对比（延伸）

前置依赖：[[#1. try/throw/catch：一次控制权转移]]、[[#3. 栈展开：异常穿过的每一层都收拾干净]]
后续衔接：[[模板]]（待产出同批）、[[数据类型与内存表示]]（int 溢出边界）

**① 它解决什么问题**

本知识点回答定位问题（任务指定立场，延伸非必需）：**算法竞赛几乎不用异常处理**。竞赛里"出错的正确姿势"是让程序在正确性上下功夫：数组开够、边界检查做在访问之前、每一步用题面给的数据范围卡死。异常机制解决的是"错误发生后体面收尾"的工程问题，而竞赛的目标是 AC——错误处理写得再优雅，答案错了还是 0 分。这一节给出两套惯例的对照表，让你在读工程代码（含 STL 源码、题解里的类封装）时不迷路。

**② 直觉理解**

模型级类比：**考试与审计**。异常机制像公司年报的审计流程——出了问题走上报、留档、问责；竞赛像闭卷考试——卷面上不允许"出错后再补救"这个环节存在，正确性必须一次做对。类比收敛到一句话：审计流程（try/catch）防的是"意外"，考试（竞赛）防的是"想不清楚"——后者靠推演，不靠异常。

用具体数字推一遍：题面 $n \le 10^5$。异常思维：开 int arr[10]，越界靠 catch 兜——RE 或 WA，分数归零。竞赛思维：先看数据范围，开 `int arr[100005]`（多开 5 个防手滑），访问前 `if (0 <= i && i < n)`——根本不给"异常"出生的机会。**复杂度账**：边界检查是每次 $O(1)$ 的固定开销，异常抛接是罕见路径的高额开销——竞赛的每一次访问都在"必经路径"上，自然选前者。

**③ 原理与推导**

两套惯例的机制对照（错误处理惯例对比）：

| 惯例 | 写法 | 适用场景 | 竞赛出现率 |
|:---:|:---:|:---:|:---:|
| 返回值错误码 | `if (ok == -1) ...` | C 风格、单层调用 | 高（隐式：判断函数返回） |
| 边界检查 | `if (0 <= i && i < n)` | 一切下标访问 | 最高（正道） |
| 断言 | `assert(i < n);` | 调试期自查，release 失效 | 中（本地调试用） |
| 异常 | try/throw/catch | 错误处理与主逻辑分离的工程 | 极低 |

**设计动机**：为什么竞赛惯例不选异常？因为异常的三项收益——错误处理与主逻辑分离、跨层传递、类型化分发——在"单文件、单 main、几百行、错误即 WA"的赛场上一项都兑现不了；而它的成本（栈展开、代码体积、心智负担）却照付。机制各有其位：异常是工程工具，不是算法工具。

**④ 代码演示**

**块一·核心代码**（自编示例：同一道"安全取值"题的两种写法对照，竞赛版为先）：

```cpp
#include <iostream>
using namespace std;
int a[100005], n;                     // 惯例一：数组开够（数据范围上界 + 余量）
int getVal(int i) {
    if (i < 0 || i >= n) return -1;   // 惯例二：边界检查做在访问之前
    return a[i];
}
int main() {
    n = 5;
    for (int i = 0; i < n; i++) a[i] = i + 11;
    cout << getVal(2) << endl;        // 13：正常路径
    cout << getVal(100) << endl;      // -1：越界返回约定值，不崩溃不抛异常
    return 0;
}
```

**块二·执行追踪表**（getVal(100) 的"无异常路径"）：

| 步骤 | 当前元素 | 结构状态 | 动作 | 结果 |
|:---:|:---:|:---|:---|:---|
| 1 | getVal(100) | n=5 | 100 < 0 不成立 | 查上界 |
| 2 | i >= n | 100 >= 5 成立 | 返回 -1 | 不访问 a[100] |
| 3 | main 接住返回值 | 无栈展开 | if 判断 -1 | 打印越界提示 |

**块三·错误写法对照**：

```diff
- int a[10]; cin >> n; for (i = 0; i < n; i++) ...   // 坑1：数组按感觉开、n 按输入来 → n>10 必越界（竞赛 RE 主因）
+ int a[100005];                                      // 按题面上界开数组（n <= 1e5）
- try { a[i] = x; } catch (...) { }                   // 坑2：用异常兜越界 → 未定义行为本就不可捕获，且白付机制成本
+ if (0 <= i && i < n) a[i] = x;                      // 访问前检查，一行解决
```

**⑤ 典型应用**

- 迁移题（自编）：读一段含 try/catch 的工程代码（可取 mycode.cpp test01），用一句话说出每个 catch 对应的业务含义。建议先独立做，再对照题解：test01 有两条路线的 catch（const char* 与 exception&），对应知识点 1、2。
- 竞赛衔接说明：竞赛里需要"看懂"异常的场合只有读工程化题解与标准库文档；真正的高频防线是三件套——数组开够（[[数据类型与内存表示]] 的溢出同源）、访问前边界检查、本地 assert 自查。下一批《模板》篇的 template<typename T> 读得懂即可，立场与本节同构。

**⑥ 坑点与边界**

> **【易错】** 用 try/catch 兜数组越界（④对照坑 2）——越界是未定义行为，不产生 C++ 异常，catch 接不住；防越界只有边界检查一条路。

> **【注意】** 本篇四个知识点的掌握深度递减：机制（1-3 节）要求"读得懂、能追控制流"，立场（本节）要求"知道几乎不用、知道正道是什么"——不必复述虚函数表级别的细节。

> [!example]-
> **边界数据集（先自己跑一遍，再展开对照）**
> 1. 空输入：n=0 且无访问 → getVal 任何调用都返回 -1（预期：空数组全越界，检查先于访问）。
> 2. 单元素：n=1，i=0 → 返回 a[0]；i=1 → -1（预期：最大合法下标是 n-1=0）。
> 3. 全相同：数组元素全同值 → 合法下标返回同值（预期：检查不影响正常路径）。
> 4. 严格递增：i=-1,0,1,...,n → 依次 -1、11、12、...、15、-1（预期：两端拦截、中间放行）。
> 5. 严格递减：i=n,...,0,-1 → 对称结果（预期：边界对称性）。
> 6. 极值：i=2147483647 与 i=-2147483648 → 两个方向的越界都被拦截（预期：检查条件用与运算符连接，两界都要查）。

回扣开场：现在你能回答开场那个定位问题了——异常机制是给"错误后体面收尾"设计的工程工具，竞赛的答案是"不给错误出生的机会"（④的结论）；机制读得懂，正道是边界检查。全篇完。

## 四、总结与自测

### 核心内容（一页纸速览）

- **try/throw/catch**：throw 抛任意表达式的值（类型即单据类别）；try 圈保护代码；catch 按类型就近接单；`catch(...)` 万能兜底；只抛不接程序终止。
- **自定义异常**：类路线——继承 exception 重写 what()，用 `catch (exception&)` 引用接；枚举路线——throw 枚举值按值分发；两套都在素材里。
- **栈展开**：异常上浮路径上每层已构造的局部对象按逆序自动析构；清理进析构函数才两头（正常/异常路径）都安全。
- **竞赛立场（延伸）**：几乎不用；正道是数组开够 + 访问前边界检查 + 本地 assert；越界是未定义行为，异常机制救不了。
- 素材中的嵌套类/局部类（p23-30）属类语法，归 [[面向对象编程]] 同批，本篇登记不重复。
