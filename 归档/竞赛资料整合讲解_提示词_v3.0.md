<constraints>
A. 讲清楚（内容质量）
1. 防跳跃：凡是源文件中出现、但不在「已掌握」清单里的新概念、术语、符号、公式，第一次出现时必须先用一句大白话解释「它是什么、为什么这里需要它」，再正式使用，绝不允许突然冒出一个没有交代的新词。「为什么定这条」：读者是零基础，一个没有交代的新词就会断掉整条理解链。
2. 不跳步：相邻推理步骤之间不得省略，补全中间过程并说明每步依据。禁用「显然」「易得」「略」「由性质可知」这类跳过推导的措辞。「为什么定这条」：对零基础读者，「显然」就是「这里讲不下去」的同义词。
3. 叙事优先：每个知识点以「问题」开场——这道题、这个现象、这个需求为什么逼出这项技术；以「现在你能解决它」收尾。讲解是一条线，不是填格子。「为什么定这条」：市面优秀资料（Hello 算法、OI Wiki）的共同点是先有动机后有定义，读者的第一个问题永远是「学它干嘛」。
4. 双层表述：同一知识点先给直觉理解（类比或小数据推演），再给严格表述（定义与推导），自带坡度。「为什么定这条」：一次性生成无法按反馈调节难度，直觉层与严格层并存可同时托住不同状态的读者。
5. 每个关键结论必须给出量级依据、类比、具体小数据推演三者之一；不得只写「更快」「更优」而不给数字。「为什么定这条」：竞赛里「快」必须落到数据规模与量级上，否则学习者无法判断能不能过题。
6. 设计动机：每个知识点的推导中至少回答一个设计动机类问题（接口为何这样设计、参数为何是这个形态、复杂度为何是这个量级）。
7. 类比须为模型级：一个类比模型要能管住一组概念（如「待结算账单」同时解释栈内单调与弹栈时机），禁止一次性散装比喻。「为什么定这条」：模型级类比可被后续知识点反复回引，散装比喻用一次就废。

B. 讲得动（语言与可读性）
8. 风格与语气：定义与结论用严格表述，解释与类比用口语短句，单句不超过 40 字为宜；避免教科书式长句堆叠与感叹式渲染。
9. 一次性生成：不向学习者提问。前置知识存疑时写入附录 B「假设清单」并继续；迁移检验题直接附完整题解，题解前加一行「建议先独立做，再对照题解」。
10. 图解优先：关键过程（执行流程、数据结构变化、几何关系）优先用 mermaid 或文本图（```text 代码块）表达，每个图后附 3 至 5 行文字版推导链（降级用）；全篇 mermaid 不超过 3 个。「为什么定这条」：Hello 算法的核心经验是「以图为主、文字为辅」，流程类内容用图讲一遍顶文字讲三遍。
11. 真题优先：⑤典型应用节优先选用源文件中的例题（注明出处：文件名或题号）与真实 OJ 题（洛谷 / 力扣题号须真实存在，禁止编造）；源文件无合适例题时自编并在题目标注「自编」。迁移检验题同样规则。

C. 排版（Obsidian 均衡档）
12. 不使用 emoji：全文任何位置（标题、正文、表格、代码注释、标签块）都不用 emoji，视觉区分一律交给 Markdown 原生能力（引用块标签、加粗、表格、分隔线）。「为什么定这条」：标注的区分度由标签语义与层级承担，emoji 只增加噪音。
13. 标注体系（callout 五子集，Obsidian 与 GitHub 双端可渲染，语义固定，不得自造标签）：callout 声明行独占一行，标签文字紧随其后作为块内首行内容；同一引用块只用一个主标签。

   |------|---------------|------|
   | 【重点】 | `> [!important]` | 必掌握结论，能遮住正文独立成句 |

D. 准确（溯源与诚实）

## 三、极限版提示词（重要主题 / 投喂弱模型时用这版）

在标准版基础上，追加以下五个模块（拼接在 `</output_format>` 之后）：

```markdown
<analysis_protocol>
动笔前，先在 <analysis> 区内完成四件事，再写正文，分析区与成品区物理分离：
1. 逐份源文件的知识点提取表：源文件名 / 提取出的知识点 / 是否在「已掌握」清单内 / 处理决策（正常讲解 / 补充讲解 / 跳过并说明理由）。
2. 合并去重说明：哪些知识点在多份源文件中重复出现，合并时采信哪份的表述。
3. 难度对标结论：源文件的最高难度点在哪里，相对「{{难度锚点}}」偏高还是偏低，计划如何拉平。
4. 拆篇判断：若本主题知识点超过 8 个，给出拆篇计划（本篇讲哪几个、后续篇名建议），本篇只完成计划内的部分。
</analysis_protocol>

<examples>
<good_example>
「为什么需要单调栈：先看一道题——给你每天的股价，问每一天之后第一次涨价是第几天。暴力做法是每个位置向右扫到底，n 天就是 O(n^2)，1e5 天就是 1e10 次比较，超时。现在换一个角度：第 5 天的股价如果比第 3 天低，那第 3 天的答案绝对不可能是第 5 天——它连第 4 天都过不去（第 4 天比它低或相等时先挡住它）。顺着这个想法，那些『还没等到更高价的日子』排成一队，恰好从队首到队尾价格越来越低——这就是单调栈。」
（好在哪里：问题开场 + 动机先行 + 直觉推演自然带出定义，无术语空降。）
</good_example>
<bad_example>
「单调栈定义：栈内元素严格单调递增或递减的栈。性质表：入栈 O(1)，弹栈 O(1)。实现如下（代码 50 行）。显然时间复杂度为 O(n)。」
（坏在哪里：定义先行无动机（读者不知道学它干嘛）、表格填格子式讲解、用「显然」跳步、无小数据推演。）
</bad_example>
</examples>

<self_review>
输出终稿前，以学习者视角通读全文一遍，逐条对照附录 C 自检清单批驳：发现跳步、未定义术语、六步残缺、知识点缺失、工程痕迹混入正文、违规使用 emoji 时当场修订，然后只输出修订后的终稿，不输出修订过程。
</self_review>

<anti_degradation>
1. 多份源文件时不得只做一份的提取表，不得合并知识点小节，不得因篇幅把六步压缩成三步。
2. 单次回复写不完时，明确声明「已讲到第 i 个知识点，剩余 i+1 至 N 待补充」并列出剩余清单，禁止静默丢弃。
3. 任何不确定的内容显式标注「这一段我不确定」或「待补充」，禁止编造公式、复杂度、来源或题号。
</anti_degradation>

<model_dialects>
- Claude：直接整体投喂，XML 标签会被严格遵循；源文件全文前置，本提示词置后。
- GPT 系：XML 标签按 Markdown 标题理解即可；要求其在分析区输出后再继续。
- 弱模型：先只发 <role>+<context>+<task>，让它复述任务与基础校准，确认无误后再分批粘贴源文件与 <output_format>。
</model_dialects>
```

## 五、设计说明（v2.5 到 v3.0 改了什么、为什么改）

| v2.5 原样 | v3.0 改动 | 理由 |
|-----------|---------|------|
| 正文开篇 4 小节「源文件覆盖对账」 | 全部移至附录 A | 用户裁决：读者打开笔记是学知识，不是验收整理过程（参照 Hello 算法 / OI Wiki：正文零工程痕迹） |
| 每知识点「六段盒子」（核心定义/逐步推导/具体例子/边界失效/疑问误解/迁移检验） | 「六步叙事」（问题开场 → 直觉 → 推导 → 实现 → 应用 → 坑点 → 回扣收尾） | 六段是验收清单的展开，叙事是学习路径的展开；讲解是一条线不是填格子 |
| 迁移检验题逐知识点必配完整题解 | 真题优先（题号+链接+思路），自编迁移题保留但降为辅助 | 真题比自编题更可信、更省篇幅；OI Wiki 体例：例题给题名+链接即可 |
| mermaid 限量 ≤2 | ≤3，并鼓励文本图讲流程 | Hello 算法核心经验「以图为主」；流程类内容一图顶千言 |
| 性质表四列固定盒子 | 融入正文一小段或小表，注明免表理由 | 表格帮助记忆、段落帮助理解；正文以理解为先，记忆交给复习版 |
| 假设登记 / 自检清单在正文 | 移至附录 B / C | 验收价值保留，阅读体验干净 |
| 防跳跃 / 不跳步 / 双层表述 / 设计动机 / 模型级类比 / 无 emoji / callout / LaTeX / 源码实测 | 全部保留 | v2.5 的内容质量纪律经实战验证有效，偏离的只是「组织方式」不是「质量要求」 |

**与 v2.5 旧产物的关系**：`笔记\单调栈.md` 与 `笔记\二分.md` 为 v2.5 产物，结构为旧六段式，内容质量已验证（lint 全通过）；用 v3.0 重新生成时可对照，旧版是否保留由用户裁决。

**改进方向**（后续可做）：
1. v3.0 产出 2 至 3 篇后，对比 v2.5 产物做可读性盲评（同一知识点两版对照），验证「叙事体」的实际收益。
2. lint 脚本已同步适配 v3.0 格式（六步叙事、附录 A/B/C、N 对 N 对账），后续主题直接可用。
